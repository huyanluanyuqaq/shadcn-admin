## Context

客户到期时间 `Customer.expireAt`（epoch ms）自系统建立即为**可空**：`null` 表示「未设置到期时间」。

它同时是三层可空的：

- 数据库列 `customers.expire_at` 可空（`server/src/db/schema.ts:76`，迁移 `0000`）；
- 写入入参 `customerInputSchema.expireAt` 为 `z.number().int().nullable().optional()`
  （`shared/src/schema/entities.ts:94`），**创建与更新共用**（`server/src/lib/crud.ts:197,224`）；
- 表单字段为 `z.date().nullable()`，默认值 `null`，编辑表单留空时占位文案为
  「长期有效（留空）」，并在对话框底部提供「清除到期时间」按钮
  （`src/features/customers/components/customers-action-dialog.tsx:687,1032-1039`）。

列表以 `daysLeft(null) → null` 派生显示「长期」（`customers-columns.tsx:147`）。

**驱动因素：**

1. **产品口径变更。** 人类先裁定「没有长期有效的选项 不需要」（TASK-040 rev3），
   即不再把「无到期约束」视为客户的一种合法业务状态；随后进一步裁定「到期时间改必填」，
   即**从产生端堵住** `null`。
2. **TASK-040 暴露的连带成本。** 续期功能必须为 `expireAt === null` 定义行为——因为该状态
   确实可由表单产生。人类裁定「不禁用、按 `now` 起算」后，其代价是这类客户一旦续期，
   便从「无到期约束」**静默转为有限期**（TASK-040 的 L8）。只要 `null` 仍可产生，
   这一语义变化就会持续发生；让字段必填是从根上终止它的方式。
3. **同一字段的两处语义分叉。** `null` 既是「长期有效」（表单占位文案）、又是「未设置」
   （TASK-040 rev3 的对话框文案），两种措辞指向同一存储状态，是文档与界面一致性的持续来源。

---

## Problem

**客户到期时间可以被留空，导致系统必须为「没有到期时间」维护一整套特殊语义。**

**展开：**

- 表单默认 `expireAt: null` ⇒ **新建客户即可能没有到期时间**；
- 「清除到期时间」按钮 ⇒ 已有到期时间的客户可被**清空**，且不触发任何提示；
- `null` 一旦存在，列表要显示「长期」、续期对话框要显示「未设置」、
  续期要么禁用要么静默改写语义（TASK-040 的 D-3 与 L8 之争即由此而来）；
- 不解决会怎样：每一处涉及到期时间的新功能，都必须重复回答「`null` 怎么办」，
  而答案只能依赖于临时裁定（TASK-040 的 rev3 就是一次这样的裁定），
  且这些裁定彼此可能不一致。
- **影响范围：** 客户表单、客户列表、续期对话框、接口契约，以及仓库内所有创建客户的调用点
  （`server/scripts/smoke.ts` 有 **10 处**载荷不带 `expireAt`）。

---

## Decision

**把 `expireAt` 变为必填：前端表单校验 + API 入参 schema 双重强制；数据库列保持可空，
历史 `null` 数据保留不动。**

**具体做法：**

1. **表单层**（`src/features/customers/data/schema.ts:87`）：
   `z.date().nullable()` → `z.date().nullable().refine((v) => v !== null, { error: '请选择到期时间' })`。
   保留 `.nullable()` 以使类型诚实（初值确实为 `null`），仅**校验**时拒绝；`zodResolver` 负责拦住保存。
2. **API 入参层**（`shared/src/schema/entities.ts:94`）：
   `z.number().int().nullable().optional()` → `z.number({ error: '请选择到期时间' }).int()`。
   ⇒ `POST` 必填非空；`PATCH` 经 `.partial()` 后仍可选，但**传 `null` 被拒**
   ⇒「不允许清空」成为契约保证。
   **校验只能加在字段上，禁止对 `customerInputSchema` 做对象级 `.refine()`**——
   `crud.ts:224` 对该 schema 调用 `.partial()`，而 zod 4.3.6 实测：含对象级 refine 的 schema
   其 `.partial()` **调用即抛** `Error: .partial() cannot be used on object schemas containing refinements`，
   会让每一次 PATCH 失败。
3. **API 输出层**（`shared/src/schema/entities.ts:108`）：在 `customerSchema` 的 `.extend({...})` 中
   **显式覆写** `expireAt: z.number().int().nullable()`。
   `customerSchema` 由 `customerInputSchema.extend()` 派生，若不覆写，`Customer.expireAt` 的类型会
   变为 `number`，而**历史行运行时仍返回 `null`** ⇒ 类型说谎。
4. **数据库层**：**不变**。不新增迁移、不回填历史 `null`（D-2）。
5. **界面**：移除「清除到期时间」按钮；占位文案改为「请选择到期时间」；
   日历加 `required` 以阻止取消选择（不生效则退化为校验兜底，但须如实披露实际行为）。
6. **契约与测试同步**：`api-contract.md` 的字段类型更新；冒烟脚本 10 处载荷补**远期** `expireAt`，
   并新增两条端到端检查（缺字段 → 400；`{ expireAt: null }` → 400）。

---

## Alternatives

### 方案 A — 仅前端表单必填（API 与数据库不动）

- **描述：** 只在客户表单加校验，隐藏「长期有效（留空）」与「清除到期时间」。
- **优点：** 改动最小（1 个文件）；无破坏性接口变更；冒烟脚本一行不动。
- **缺点：** API 仍可创建与清空 `null`；`null` 的产生端并未关闭，只是**默认路径**被堵住；
  任何直接调用 API 的路径（脚本、未来的新界面）仍会产出 `null`。
- **未采纳原因：** 人类裁定采用「表单 + API 入参」层级。本方案把「必填」变成了**界面约定**而非
  系统契约——按本仓库的审查纪律（「声称」与「实际」必须一致），这是最容易被判为名义达成的形态。

### 方案 B — 表单 + API + 数据库 `NOT NULL` + 回填历史 `null`

- **描述：** 在方案（本 ADR 的 Decision）基础上，把 `customers.expire_at` 改为 `NOT NULL`，
  并写一条迁移把全部历史 `null` 回填为指定日期。
- **优点：** 保证强度最高——`null` 在存储层即不可能存在；`isNotNull` 类过滤、`null` 分支代码
  可陆续清理。
- **缺点：**
  - SQLite 无法直接 `ALTER COLUMN`，需**重建表**迁移（`0000` → `0002` 已有先例，可做但不可逆性更高）；
  - 必须为历史 `null` 行**单方面指定**一个到期日期，而「无到期时间」原本可能正是那些客户的真实意图
    —— 这是一次**不可回溯的业务语义改写**；
  - 与人类选定的「`null` 只存在于历史数据里」的表述直接冲突：回填后 `null` 将完全不存在，
    TASK-040 续期对话框的 `null` 分支随之成为死代码，需回头改 TASK-040 的既有设计。
- **未采纳原因：** 人类裁定「保留，编辑时补填」（而非「一次性回填」，见人类三选一裁定）。
  本 ADR 的 D-2 即为该方案的正式被否记录；若将来确要消除 `null`，须另立 ADR 重新论证回填口径。

### 方案 C — 不做变更（保持可空与「长期有效（留空）」）

- **描述：** 维持现状，`null` 继续表示「长期有效」。
- **优点：** 无迁移成本、无接口变更、无测试改动。
- **缺点：** 与人类裁定「没有长期有效的选项 不需要」冲突；每一处新功能都要继续回答
  「`null` 怎么办」，而 TASK-040 已证明这类答案只能是临时裁定（且被裁定为「不禁用 + 静默改写」，
  即已知的 L8）。
- **未采纳原因：** 产品已明确不需要该状态。

### 方案 D — 输出 schema 也改为必填（`Customer.expireAt: number`）

- **描述：** 连 `customerSchema`（API 输出）也去掉 `.nullable()`，让类型层面「彻底没有 `null`」。
- **优点：** 类型看起来最干净；可逐步删除前端所有 `null` 分支。
- **缺点：** 与 D-2 冲突——历史行在数据库里**确实是 `null`**，输出被声明为非空即为**类型说谎**，
  且任何基于 `customerSchema` 的输出校验都会在历史数据上失败。
- **未采纳原因：** 类型必须如实描述数据（含历史数据）。`null` 的消失应由**数据**决定，
  而不是由类型的乐观声明决定。

---

## Consequences

### 正面

- **`expireAt` 成为真实不变量**：无论从表单还是 API，都无法再产生 `null`；「不允许清空」由 schema 保证。
- 「长期有效」这一概念的表单入口（占位文案）与清除入口（按钮）同时消失，`null` 退化为
  **纯历史状态**——TASK-040 的 rev3 裁定所依赖的「该状态可达」将收窄为「历史数据可达」。
- 改动集中在两个 schema 与一个界面文件；**无迁移、无新依赖、服务端零改动**。
- 契约获得**端到端证据**：冒烟新增「缺字段 → 400」「传 `null` → 400」两条检查。

### 负面

1. **破坏性接口变更：** `POST /api/customers` 由「`expireAt` 可省略」变为「必填」。
   仓库内调用点已穷举（`server/scripts/smoke.ts` 10 处，设计文档 F8），但任何**仓库外**调用方
   会收到 400。缓解：本系统为内部应用，未发现仓库外调用方；变更写入 `api-contract.md` 与 CHANGELOG 式说明。
2. **编辑历史客户被强制补填：** 即使只想改备注，也必须先设一个到期时间（设计文档 L1）。
   这是「必填」的固有含义，不是缺陷；缓解手段为字段级错误提示与「购买时间 + 档位」自动计算路径。
3. **保证强度止于 API 层：** 数据库列仍可空，直写 DB 或未来绕过 CRUD 的写入仍可置 `null`（L2）。
4. **类型与入参的表观矛盾：** 输出类型保留 `number | null` 而输入必填，读者可能误判为不一致（L3）。

### 中性 / 需要注意

- **订阅实体的 `expireAt` 明确不在本 ADR 范围内**（`shared/src/schema/entities.ts:157`，
  其界面亦有「长期有效（留空）」与清除按钮）。其 `expireAt` 由**同步引擎**写入
  （`server/src/services/subscription-sync.ts`），上游可能不返回 ⇒ 强制必填会与同步语义冲突。
  ⇒ 两个实体的到期时间语义从此**不同**，须在文档中明示，避免审查者误判为漏改。
- **TASK-040 的文档随之滞后：** 其 F13 / L8 / §3.4 以「新建表单默认 `null`」作为可达性证据，
  本 ADR 落地后该表述失效 ⇒ 须同步补一行注记（范围严格限于注记）。
- 「列表 `null` 文案改为『未设置』」（D-3）**已由人类于 2026-10-16 追认生效**，无待决的撤销分支；
  该文案的改动点仅 `customers-columns.tsx:147` 一处，实施时按「未设置」执行。
