## Context

系统里已经存在一处「月」的口径，本次新增的「客户续期」是第二处，二者的关系需要显式裁决。

**既有口径（套餐档位）：** 套餐的价格档位在 2026-10-10 定为四档，其周期长度以**固定天数**表达：

```ts
export const planTiers = [
  { value: 'monthly',    label: '月付', days: 30,  priceKey: 'priceMonthly' },
  { value: 'quarterly',  label: '季付', days: 90,  priceKey: 'priceQuarterly' },
  { value: 'semiannual', label: '半年', days: 180, priceKey: 'priceSemiannual' },
  { value: 'yearly',     label: '年付', days: 360, priceKey: 'priceYearly' },
] as const
```

（`shared/src/schema/entities.ts:49-54`）
客户创建/编辑时的到期时间由 `computeExpireAt(purchasedAt, days)` 用 `addDays` 推出
（`src/features/customers/data/schema.ts:207-213`）；`splitPlanCycles` 进一步按**自然月**推进
周期边界，但其锚点为购买日、末周期以到期时间截断（`src/features/customers/utils.ts:83-114`）。
⇒ 即：**套餐的「时长」是固定天数，「周期展示」才按月推进**。

**本次新增的能力（用户指令，2026-10-16）：** 「客户管理页面中，用户在数据列表中选中某一行后，
点击『续期』弹出选择框，提供 1 个月 / 3 个月 / 6 个月 / 12 个月四个快捷选项，
并额外提供可手动输入天数的输入框。」——即**同一功能内同时存在「月」与「天」两种表达**，
且「月」出现在用户可见文案里。

**驱动因素：**

1. 续期需要对**已过期客户**与**未过期客户**给出统一且可预期的结果。
2. 客户到期时间（`Customer.expireAt`，epoch ms）是运营的**收款依据**，
   其计算口径不可含糊或随实现细节漂移。
3. **（2026-10-16 人类裁定）** 续期的「月」**必须与套餐档位同口径**：套餐本就以固定天数计价与计时，
   续期若另立自然月口径，同一系统内就出现两种「月」，实现、测试、运营三处都要永久区分，
   长期必然漂移；单一口径优先于「个月」的字面直觉（代价见 Consequences 负面第 1 条）。
4. **（2026-10-16 人类裁定）** `expireAt === null` **不作为本功能的业务特例**：人类明确
   「没有长期有效的选项 不需要」⇒ 不为其增设禁用条件或专门入口。
   但代码实证该状态**可达**（见下），故仍须定义其计算结果与界面呈现。

**关于 `expireAt === null` 的实证（决定 D-3 必须"定义行为"而非"忽略"）：**

| 证据 | 位置 |
|------|------|
| 新建客户表单默认 `expireAt: null` | `src/features/customers/data/schema.ts:121` |
| 编辑表单该字段留空时占位显示「长期有效（留空）」；日历可清除已选日期 ⇒ 回到该状态 | `customers-action-dialog.tsx:676-690`（`onSelect(date ?? null)`） |
| 列表「剩余天数」列对该状态显示「长期」；`daysLeft(null) → null` | `customers-columns.tsx:143-148`；`utils.ts:40-43` |
| 共享 schema 允许 `expireAt` 为 `null` | `shared/src/schema/entities.ts:94` |

⇒ 人类裁定「不存在该选项」指的是**不把它当作业务选项来设计规则**；但数据层允许且默认为 `null`，
因此本 ADR 必须给出确定的计算与呈现（否则纯函数会产出 `NaN` 或静默改写语义）。

## Problem

续期把「时长」换算成「新的到期时间」时，必须回答三个否则会由实现细节随机决定的问题：

1. **「个月」按什么算？** 自然月（日历月，`addMonths`，月末自动 clamp）还是固定天数（30/90/180/360）？
2. **从哪个时刻起算？** 从**原到期时间**顺延，还是从**今天**重新计算？
3. **`expireAt === null` 的客户怎么办？**（不设特例 ⇒ 但仍需确定"算出来是什么"）

**不解决会怎样：**

- 口径不定 → 前后端、测试与运营手册各写一套；同一客户两次续期结果不一致，
  且事后无法判断是缺陷还是设计。
- 基准不定 → 「已过期客户续期后到期时间比预期早 N 天」这类投诉无法定性；
  若默认为「从今天重算」，未过期客户会被静默吞掉已付费的剩余天数（**直接的钱的问题**）。
- `null` 处理不定 → 纯函数在收到 `null` 时可能产出 `NaN`；或在界面上无任何提示地
  把「无到期约束」改写成有限日期（**变更不可见**）。

> **本轮结论：Q1 已由人类裁定 ⇒ 固定天数（与档位统一）；Q3 已由人类裁定 ⇒ 不设特例、
> 按 `now` 起算且界面显示基准。** 两者的原始提案均作为**被否方案**保留在 Alternatives，
> 其被否理由与代价如实登记。

## Decision

**三项决策如下（与 `docs/technical/customer-renewal.md` §5 一致，该文为实现依据）：**

### 采纳项

| # | 问题 | 决策 |
|---|------|------|
| **D-1** | 「个月」按什么算 | **固定天数，与套餐档位统一**：`1 / 3 / 6 / 12 个月 → 30 / 90 / 180 / 360 天`（天数值 = `planTiers` 各档的 `days`）。手动输入的天数同样走天数。⇒ **本功能只有「天」一种单位**，「个月」仅是快捷项文案，内部不存在 `addMonths` 路径 |
| **D-2** | 从哪个时刻起算 | **基准 `base = max(expireAt, now)`** —— 未过期客户自**原到期时刻**顺延（保留已付剩余时间与时分秒）；已过期客户自 **`now`** 起算（不补回已过去的空窗期） |
| **D-3** | `expireAt === null` 如何处理 | **不设特例、不禁用**：该客户**正常参与续期**，基准取 `now`（与「已过期」共用同一表达式）⇒ 结果 = `addDays(now, days)`。**界面必须呈现基准**：对话框只读行显示 `当前到期：未设置`，预览行追加 `（自今日起算）` 并给出具体新到期时间（`customer-renewal.md` §4.5） |

**公式（唯一实现形态）：**

```
base        = expireAt == null ? now : max(expireAt, now)
newExpireAt = addDays(base, days)

days = 快捷项 → planTiers 对应档位的 days（30 / 90 / 180 / 360）
       自定义 → parseRenewDaysInput(raw)（1–3650 的整数；非法为 null ⇒ 禁止提交）
```

**单一单位是 D-1 的直接结果：** 没有「月/天」单位分支，没有月末 clamp 分支，
纯函数签名为 `computeRenewedExpireAt(expireAt, days, now)`（见设计文档 §5.2）。
**`null` 不做特例分支是 D-3 的直接结果：** `expireAt == null ? now : max(...)` 一个表达式同时覆盖
三种情形（未来顺延 / 已过期 / 未设置），UI 层不再需要第 4 条禁用条件（设计文档 §3.4 由 4 条收敛为 3 条）。

### 实现约束（由 D-1 / D-3 派生，实施必须遵守）

1. 快捷项天数以**字面量常量**声明在 `src/features/customers/utils.ts`
   （`RENEW_PRESET_DAYS = { m1: 30, m3: 90, m6: 180, m12: 360 }`），并以**单测对齐** `planTiers`：
   `expect(RENEW_PRESET_DAYS.m1).toBe(planTiers.find(t => t.value === 'monthly')?.days)`（四档同）。
   - **为何不直接派生（`RENEW_PRESET_DAYS.m1 = planTiers[0].days`）**：派生会让档位变更**静默**改变
     续期语义；字面量 + 对齐单测则在档位变更时**报警并阻断 CI**，把决策权交回人类，
     与 D-1 的裁定链路（人类裁定 → 文档 → 代码）一致。索引式派生（`planTiers[0]`）另有
     重排后静默错配的风险，更不可取。
2. **UI 必须把天数显示出来**：每个快捷项同时展示对应天数（`1 个月 30 天`），预览行增量用
   `（+N 天）` 表述，**不做**「+1 个月」的措辞。理由：操作者需在提交前就能自行验算结果，
   这是 §「负面 1」月末漂移的唯一现实缓解手段。
3. **UI 必须呈现基准（D-3 的必要条件）**：只读行须区分三种基准（`自原到期时间顺延` /
   `已过期 N 天` / `未设置`），预览行必须给出**具体的新到期时间**。理由：`expireAt === null`
   的客户续期后会由「无到期约束」变为有限日期，该变化必须**在提交前可见**，
   否则即成为"静默改写语义"（这正是原方案 E 的反对理由，见 Alternatives）。
4. **不得引入 `addMonths` 作为续期路径**。`utils.ts` 中的 `addMonths` 是 `splitPlanCycles` 的既有依赖，
   **不因本决策被移除**——勿以「未使用」为由清理该导入。

### 明确不做（本 ADR 的边界）

- **不**改动套餐档位 30/90/180/360 天口径（本决策正是**沿用**它）。
- **不**引入第二种「月」的定义（自然月被否决，见方案 A）。
- **不**为 `expireAt === null` 增设禁用条件、专门按钮或专门入口（D-3）。
- **不**引入 UTC 口径（与既有 `formatDateTime` / `daysLeft` / `splitPlanCycles` 的本地时区语义保持一致）。
- **不**为续期记录专门的「原到期 → 新到期」流水（含 `null → 有限` 的转换记录）。
- **不**引入乐观锁（`expireAt` 的并发覆盖为已知限制，见 `customer-renewal.md` §4.7）。

## Alternatives

### 方案 A — 自然月（`addMonths`，月末自动 clamp）—— **2026-10-16 被人类否决（rev2）**

```
newExpireAt = addMonths(base, months)   // 1/3/6/12 个月 → 日历月
```

**优点：** 贴合「1 个月」的字面直觉；`2026-01-31 + 1 个月 = 2026-02-28`（月末自动取当月最后一天）；
闰年无需特判。**这正是首轮设计稿采纳该方案的唯一理由。**

**缺点（决定性）：**

- **与套餐档位并存两种「月」**：全系统将永久存在「套餐的月 = 固定天数」与「续期的月 = 自然月」
  两套定义，实现、测试、运营手册三处都要区分；同一客户「剩余天数」与「周期末」可比性下降，
  且任何一处的后续演进都会加剧分叉（这正是驱动因素 3 所指的长期成本）。
- **字面直觉并不能消除歧义**：「1 个月」到底落 `02-28` 还是 `03-02`，两种答案都不易被操作者预测；
  真正的风险不是二选一的结果，而是**同一系统内两套并存且各自都"看起来对"**。
- 人类已明确裁定「主张与档位统一」，本方案出局。

**结论：不采纳。** 其代价（月末与闰年的日历漂移）转移为采纳方案的已知缺点，
见 Consequences 负面第 1 条（**必须如实登记为刻意行为**）。

### 方案 B — 一律自今日重算（`base = now` 恒定）

**优点：** 实现最简，无分支；`max(...)` 不需要。

**缺点（决定性）：** 未过期客户被**吞掉已付费的剩余天数**。客户到期日为 6 个月后时续期 1 个月，
新到期日变为「今天 +1 个月」，等于客户损失 6 个月——这是直接的资损与信任问题。

**结论：不采纳。** 注意与 D-3 的区别：D-3 的「自今日起算」**仅**适用于 `expireAt` 为 `null`
或已过期（无剩余时间可保留）的客户，不影响未过期客户的顺延语义。

### 方案 C — 允许 `expireAt === null` 续期，自今日起算 —— **2026-10-16 由人类裁定采纳（rev3）**

> 本方案在首轮设计中被列为**被否项**（理由见下），人类于 rev3 明确
> 「没有长期有效的选项 不需要」后**转为采纳**，即 Decision 的 D-3。此处保留其原始反对意见，
> 因为它们正是**实现约束 3（界面必须呈现基准）**的由来——反对理由没有被忽略，而是改为
> 「用可见性替代禁用」来缓解。

```
base = now（当 expireAt === null）
```

**原始反对意见（首轮设计，现被"缓解"而非"采纳其结论"）：**

- 「长期有效」在语义上意味着**没有到期约束**；对其施加有限期限是一种**语义变更**。
- 一旦操作，客户从「无约束」变为「某日到期」，属于对客户权益的实质影响。
- 原设计据此要求「操作者若确实要设定到期时间，应走『编辑』表单（显式字段 + 显式提交）」。

**为何改判（人类裁定 + 事实校正）：**

- 人类明确该情形**不作为业务选项**，即不希望为一个"未设置"的数据状态增设产品规则
  （额外禁用态会带来：多一次点击、错误提示、以及"为什么这个客户不能续期"的解释成本）。
- 实证（见 Context 表）显示 `null` 更接近**"未填写"**而非"刻意声明永久有效"：
  它是新建客户的**默认值**，表单占位文案为「长期有效（留空）」。
- 原始反对意见的真正内核是**"变更不可见"**，而非"变更本身有害"：
  只要对话框在提交前显示 `未设置` + `（自今日起算）` + 具体新到期时间，
  操作者即可自行判断是否继续。⇒ 以**可见性**替代**禁用**（实现约束 3）。

**代价：** 数据中若确有此类客户，一次续期即把「无约束」改写为具体日期，且无专用流水（L8）。
**缓解：** 变更在提交前可见；如需保留"真正的长期客户"概念，须另立任务（含数据侧如何表达）。

### 方案 D — 引入独立续期端点 `POST /api/customers/:id/renew`

**优点：** 服务端可原子化「读现值 + 计算 + 写入」，天然规避并发覆盖；便于加专用审计。

**缺点：** 与既有 `PATCH /api/customers/:id` 能力重复（该端点已支持仅提交 `expireAt`）；
新增端点属接口契约变更，需同步 `docs/technical/api-contract.md` 与共享 zod schema，
并为本功能的**单字段更新**引入额外的长期维护面。

**结论：不采纳**（在需要「服务端权威计算」或专用审计流水时，应作为独立任务重新评估，
届时并发问题（方案 D 的主要收益）须一并论证）。

### 方案 E — 对 `expireAt === null` 的客户**禁用续期**，引导走「编辑」（首轮设计，**2026-10-16 被人类否决**）

**内容：** 按钮在选中该类客户时 `disabled`，提示 `长期有效的客户无需续期，请用「编辑」直接设置到期时间`。

**优点：** 杜绝「无约束 → 有限期」的意外改写；操作者若确实要设定到期时间，
「编辑」表单的显式字段是更明确的路径。

**缺点（决定性）：**

- 人类明确**不存在该业务选项、不需要**该规则 ⇒ 禁用条件会对一个"未填写"的数据状态
  施加产品级限制，与实际语义不符。
- 实例化成本：该状态是**新建客户的默认值**，禁用会使「新建后未填到期时间的客户无法从工具栏续期」
  成为常见路径，而引导文案（「请用编辑设置到期时间」）会把一个正常操作变成两次操作。
- 变更可见性可由界面承担（实现约束 3），无需以禁用作为唯一保障。

**结论：不采纳。** 其安全目标（避免静默改写）由 D-3 的界面呈现要求继承。

## Consequences

### 正面

1. **资损风险为零**：未过期客户的剩余时间与到期时刻都被完整保留（D-2）。
2. **口径唯一（D-1 的核心收益）**：全系统只有「月 = 档位固定天数」一种定义；续期、`computeExpireAt`
   （`addDays`）与套餐计价同源，不再出现「两套月」的解释困境，运营手册只需一句话。
3. **实现与测试面积最小**：单一 `addDays` 路径 + 单一基准表达式 ⇒ 无单位分支、无月末 clamp 分支、
   无用例二分；**禁用矩阵由 4 条收敛为 3 条**（D-3）；算法收敛为 `utils.ts` 中的一个纯函数。
4. **已过期与未设置客户行为可预期**：二者共用「自今日起算」，且对话框直接显示这一事实
   （`（自今日起算）` 标注），无需口头约定。
5. **与档位的对齐是可检验的**：天数以字面量声明 + 单测对齐 `planTiers`（实现约束 1），
   档位若变更会**阻断 CI** 而非静默漂移。
6. **无"死代码"**：`base` 的 `null` 分支是 UI 可达的正常路径（D-3），实现与测试都必须覆盖它，
   而不是把它当作永不执行的防御性代码。

### 负面

1. **月末与闰年出现日历漂移（D-1 的代价，接受）**——具体形态必须被逐条登记，避免被误判为缺陷：

   | 场景 | 结果 | 与自然月口径的差异 |
   |------|------|-------------------|
   | `2026-01-31` 续 1 个月（30 天） | **`2026-03-02`** | 自然月口径为 `2026-02-28` |
   | `2026-08-31` 续 6 个月（180 天） | **`2027-02-27`** | 自然月口径为 `2027-02-28` |
   | `2027-01-22` 续 12 个月（360 天） | **`2028-01-17`** | 比自然年短 5 天（跨闰年 6 天） |

   **缓解：** ① 对话框在每个快捷项上直接显示对应天数（`1 个月 30 天`）与预览增量（`+360 天`），
   使结果在提交前可算可验；② 需要精确到某日时，可用「自定义天数」输入（本例输 `365` 即得
   `2028-01-22`）或在「编辑」中直接设定到期日；③ 登记为 TASK-040 的 Known Issue（L5）。
2. **「不得修正」需要被反复声明**：凡见「`1/31` 续 1 个月得 `3/2`」，**不得**改回 `addMonths`
   ——那属于本 ADR 方案 A 的重议范围，不是缺陷修复。该声明同时写入设计文档 §8 L5、
   TASK-040 Notes 与本 ADR，三处互为防线。
3. **`null` 客户被改写为有限期（D-3 的代价，接受并披露）**：数据中若确有 `expireAt === null`
   的客户（新建默认值），续期一次即把「无到期约束」变为具体日期，且无专用流水可回溯（L8）。
   **缓解：** 变更在提交前对操作者可见（`未设置` + `（自今日起算）` + 具体新到期时间，实现约束 3）；
   如需保留"真正的长期客户"概念，须另立任务（含数据侧如何表达，例如显式布尔字段而非 `null`）。
4. **并发覆盖风险未解决**：`max(expireAt, now)` 基于客户端快照计算，服务端无版本校验，
   存在 last-write-wins 窗口。**缓解：** 如实登记（L1）；若业务上出现并发编辑，应另立任务
   引入前置条件校验（`expectedUpdatedAt` + 409），届时本 ADR 需补充或出新 ADR。

### 中性 / 需要注意

- **`planTiers` 是续期天数的事实来源，但以「字面量 + 单测对齐」方式耦合**（实现约束 1）：
  这既保留了可读性，又把档位变更转化为一次显式的、可见的决策，而非静默跟随或静默错配。
- **`null` 分支必须是可达且被测的**（D-3）：`expireAt == null` 在 UI 层不再被拦截，
  因此**不得**把该分支当作「永不执行的防御性代码」而在审查中放过；反之，也**不得**为它
  恢复禁用条件或抛出异常（与人类裁定相悖）。设计文档 §7.1/§7.2/§7.3 均列有对应用例。
- **本 ADR 不改变列表对 `null` 的展示文案**：`daysLeft(null) → null` → 列表文案（F2）由**另一项决定**
  约束 —— TASK-041 / ADR-005 的 D-3 将该文案由「长期」改为「未设置」，并已由人类于 2026-10-16 追认。
  本 ADR 只改变「该状态能否续期」与「续期后基准如何呈现」；上文与 References 中出现的「长期」
  均为**改动前时点**的代码实证记载。
- **`addMonths` 导入保留**：`splitPlanCycles`（周期展示）仍依赖它，与续期无关。见实现约束 4。
