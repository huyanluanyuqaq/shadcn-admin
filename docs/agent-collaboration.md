# Agent 协作流程（GitHub）

> **目的：** 规定本仓库中两个协作位（主控位 / 执行位）如何以 GitHub 为载体完成一个任务，
> 以及**哪些约定由平台强制、哪些只靠流程自觉**。
>
> **本文件是仓库内自持的说明。** 自 TASK-039（2026-10-15）起，`.agents/` 协作框架已随本仓库
> 版本化（逐字复制自 Workspace 模板仓库），独立 clone 后同样可读；本文件是其上的**项目级流程摘要**，
> 与 `.agents/protocols/github-collaboration.md` 不一致时以框架原文为准。
>
> 相关文档：[`git-workflow.md`](./git-workflow.md)（分支与提交）、
> [`operations/github-capability.md`](./operations/github-capability.md)（平台能力与实测事实）。

## 1. 两个协作位

角色**不绑定任何 Agent 产品或模型**。同一个 Agent 实例可以在不同任务中承担不同协作位，
但**必须在该任务中明确当前是哪一位**。

| 协作位 | 职责 | 不做 |
| ------ | ---- | ---- |
| **主控位 Coordinator** | 理解需求、定义验收标准、拆分与分配、审查实际差异、判定验收、回写任务记录 | 不在未接管任务时直接覆盖执行位的代码 |
| **执行位 Implementer** | 检查仓库状态、在授权范围内建分支、实施与自测、创建交付请求、按审查意见整改 | 不擅自扩大范围、不覆盖他人未提交修改、不绕过门禁、不隐瞒失败 |

**审查独立性：** 审查必须由**与实现不同的会话/实例**完成。
若同一实例既实现又审查，必须在任务文件的 `Known Issues` 中记录
「审查为自我审查，未经独立验证」。**自我检查不等于独立审查。**

## 2. 三层载体与唯一事实来源

```
层 1 文件层（唯一事实来源，随仓库版本化，离线可用）
    tasks/<state>/<task-id>/TASK.md      状态、范围、验收标准、已知问题
    tasks/<state>/<task-id>/handoffs/**  交接、审查、整改记录（含命令原始输出）
    docs/**                              架构、规范、运维
    AGENTS.md                            项目规则入口
        │ 单向投影（文件 → 平台）
        ▼
层 2 平台层（协作与门禁，需权限，不承载不可再生信息）
    工作分支 / 提交 / 交付请求(PR) / Actions / 默认分支
        │ 人类授权
        ▼
层 3 授权层（不可自动化，受保护）
    高风险操作批准、发布授权、规则与权限变更批准
```

**四条不可违反的层间规则：**

1. **平台不是状态源。** 任何「只存在于平台、未落文件」的信息视为不存在。
2. **PR 不产生新信息。** 它是层 1 的渲染；**禁止只在 PR 里写信息而不回写任务文件**。
3. **层 1 缺失即阻断。** 没有任务文件的任务，**不得**创建 PR。
4. **Actions 与 Agent 均不得**自行批准层 3 的操作。

**进度总览**（项目看板、Issue 等）只能是只读汇总，**不得**成为第二套状态来源。

## 3. 端到端流程（10 阶段）

| 阶段 | 协作位 | 做什么 | 完成的标志 |
| ---- | ------ | ------ | ---------- |
| 0 执行前检查 | 主控位 | 确认仓库、分支、工作区状态 | 工作区**无**未提交变更 |
| 1 需求登记 | 主控位 | 写 `tasks/active/<task-id>/TASK.md` | 背景/目标/范围/排除范围/验收标准/约束/依赖/风险/审批要求/验证要求齐全 |
| 2 方案与分配 | 主控位 | 定实施方案与文件边界、查重 | 边界明确、依赖满足 |
| 3 认领与再检查 | 执行位 | 六项检查：仓库、分支、工作区、规范、可行性、授权范围 | 认领信息写入 `TASK.md`（Owner / Owner Since） |
| 4 分支隔离 | 执行位 | 从最新 `main` 派生工作分支并**推送到远端** | 分支已推送（防仅存本地而丢失） |
| 5 实施与提交 | 执行位 | 小步实施、本地自测、原子提交 | 本地检查全绿；无调试残留与密钥 |
| 6 交付请求 | 执行位 | 创建 PR（建议先 Draft） | PR 描述覆盖 [§5](#5-交付请求描述的来源) 全部字段 |
| 7 机器验证 | Actions | CI 在 PR 上运行 | 全部必需检查通过 |
| 8 主控审查 | 主控位 | 读**实际差异**（不只读描述）逐项给结论 | 结论（PASS / 待整改）写入 `handoffs/` |
| 9 整改与复审 | 执行位 → 主控位 | 同分支追加提交 → 复审 | 阻断项关闭且**经复核**，而非仅标记已解决 |
| 10 合并与归档 | 主控位 | 按 `git-workflow.md` §4 合并、回写 `TASK.md` | Merge Record 含 PR 号与 CI run id |

> **关于 Issue：** 本仓库的 Issues **已于 TASK-056 关闭**（2026-11-02 实测 `has_issues=false`）。
> 关闭前的状态是「开启但不可用」—— 唯一入口是指向上游仓库 Discussions 的 `contact_link`，
> 且 `blank_issues_enabled: false`，因此本仓库**建不出任何 Issue**，历史记录为 0 条。
> 任务状态一律以 `tasks/**/TASK.md` 为准，平台上**不存在**第二套状态来源。
>
> **本决策不依赖 Issues 的开关状态。** 无论启用与否，都保持「文件为唯一事实来源」，
> 理由是**避免双写**、仓库被单独 clone 后任务状态仍然完整、以及单一平台身份下
> Issue 无法承担「谁批准了谁」的状态机 —— 而不是「Issues 不可用」。
> 平台事实会漂移（该值曾经历 `false → true → false`）：引用
> [`operations/github-capability.md`](operations/github-capability.md) §8 前须重新实测。

## 4. 检查与门禁

必需检查的**权威声明在本仓库 `AGENTS.md` §14**（避免两处维护）。
CI 的触发条件与作业名以 `.github/workflows/ci.yml` 为准。

**判断一个检查是否构成门禁的唯一标准：它是否在合并之前运行。**
只在合并后才触发的检查，无论多绿，**都不是门禁**——它是在代码已经落地之后才跑的。

**可追溯性检查（TASK-056 新增）：** `scripts/check-traceability.py` 已在 CI 中作为
`traceability` 作业运行，校验 PR 内每个提交的 `Refs: TASK-NNN` 且该任务真实存在。
**但它尚未被加入分支保护的必需检查**，因此**当前不构成门禁** —— 它的状态以
`AGENTS.md` §14.1 与 `operations/github-capability.md` §3 的实测值为准。

**禁止**为使检查变绿而删除测试、放宽断言、伪造结果或绕过保护规则。

## 5. 交付请求描述的来源

PR 描述**不产生新信息**，它是层 1 的渲染：

| PR 字段 | 数据来源（层 1） |
| ------- | --------------- |
| 关联任务 | `TASK.md` 的 Task ID + 提交 footer 的 `Refs:` |
| 变更摘要 | `TASK.md` 的 Objective |
| 实现内容与范围 | `TASK.md` 的 Requirements / File Scope |
| 测试结果 | `TASK.md` 的 Verification + `handoffs/` 中命令的原始输出 |
| 未执行的测试及原因 | `handoffs/` 的 Tests + `TASK.md` 的 Known Issues |
| 兼容性 / 安全 / 部署影响 | `handoffs/` 的 Assumptions + Risks |
| 回滚方案 | `handoffs/` 的 Risks（回滚段） |
| 遗留问题 | `TASK.md` 的 Known Issues |
| 执行者自检 | `handoffs/` 的交接检查清单 |

**若某字段在层 1 无对应内容 → 补齐层 1，而不是只写在 PR 里。**

模板：[`../.github/PULL_REQUEST_TEMPLATE.md`](../.github/PULL_REQUEST_TEMPLATE.md)

## 6. 必须披露的落差（制度 ≠ 平台强制）

**规则写得再严，平台不拦就等于没拦。** 下表必须与
[`operations/github-capability.md`](./operations/github-capability.md) §5 **逐行一致**（同 8 行、同列）——
**修改其一必须同步修改另一处**（TASK-031 曾因只改一侧而产生一次不实断言）。

「**保证来源**」列区分三类：**平台设置**（由 GitHub 强制）；**仓库文件**（随版本化，
不由平台强制但**不依赖人的自觉**）；**自觉（约定）**（既不平台强制、也不由文件保证）。

| 文档约定 | 平台是否强制 | 保证来源 | 说明与补救 |
| -------- | ------------ | -------- | ---------- |
| 禁止直接推送默认分支 | **是**（2026-10-14 起） | **平台设置**（经典分支保护：「要求合并前必须经过 PR」） | 已实测：以**所有者身份**直推被 `GH006` 拒绝（能力记录 §4 V1 / V2）。⚠️ **平台配置不在版本历史内**，其新鲜度无法自证，见能力记录 §8 |
| 合并前必须通过必需检查 | **是**（2026-10-14 起） | **平台设置**（`install-lint-build` + `audit`） | 已实测：红灯 PR 的合并被服务端以 **HTTP 405** 拒绝（能力记录 §4 V4） |
| 合并策略为 `rebase-merge`（不留 merge commit） | **否** | 自觉（约定）+ 仓库文档 | `required_linear_history` **未启用**，平台不会阻止 merge commit；如需强制须另开该选项（能力记录 §2） |
| 实现者 ≠ 批准者 | **否**（单一平台身份） | 自觉（约定） | 必需批准数固定为 **0**，平台**不提供**第二人批准；靠换会话审查 + `Known Issues` 披露 + 证据落 `handoffs/` |
| 合并前必须经过实质审查 | **否** | 自觉（约定） | 审查证据必须落到 `handoffs/` |
| 提交信息 / 分支命名规范 | **否** | 自觉（约定） | 由约定与后续自动化检查承担 |
| 合并与对外发布解耦 | **否**（平台不强制任何发布行为） | **仓库文件**（`docker.yml` 的 metadata `enable=${{ github.ref_type == 'tag' }}` 门禁） | 合并**会**产出 `sha-*` 镜像，但 `latest` 仅在 tag 时前进；拦截点是 metadata 门禁，**不是触发器**（触发器对 `main` 与 tag 均开启）。实测见 `operations/github-capability.md` §4 |
| 高风险操作需人类批准 | **否** | 自觉（制度门禁） | —— |

> **固定披露项：** 两个协作位共用同一平台身份时，平台审计**无法区分**
> 「执行位的自我确认」与「主控位的独立审查」。这一点不接受"看起来没问题"了事。

## 7. 多 Agent 扩展

当前制度以**双协作位**为基本模型。扩展到多 Agent 时：

1. 先拆子任务、明确模块边界与接口，再并行；
2. 指定**唯一的集成责任位**汇总，禁止多个位无协调地改同一分支或同一文件；
3. 每个位仍必须明确「属于哪一协作位」，不得因为人多而模糊审查责任。
