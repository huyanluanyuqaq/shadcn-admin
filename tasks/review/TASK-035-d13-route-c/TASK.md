## Design Decisions

### D1 · 选项 C 的精确含义与「终止规则」

- **做法：** 合并后的回写（`Status → DONE` + 移入 `tasks/done/` + 回写 `Merge Record`）**并入下一个任务的交付请求**；
  **永不单独开「回写专用」请求**。任务在**提交审查时**即转 `REVIEW` 并移入 `tasks/review/`，
  并**停留于此**直到下一个任务补齐归档。
- **回归终止：** 因为永不产生「回写专用请求」，§6 要求的「**回写请求自身的合并标识**」这一项**根本不存在** ⇒
  **回归终止于深度 1**：任何 `Merge Record` **至多延后一个任务**补记。**选项 D 因此在 C 下不再需要。**
- **已接受的代价（须如实记录）：** 协议 §9 的「任务状态与物理目录一致」检查，在该窗口内**不成立**
  （任务处于 `REVIEW` 且确在 `tasks/review/` —— 状态与目录其实**仍自洽**，
  未完成的是「**已合并却仍标 REVIEW**」这件事）。该窗口的存在是**裁决的一部分，不是缺陷**。

### D2 · 本任务**直接以 `REVIEW` 提交**（不经 `ACTIVE` 的提交）

- **做法：** 档案直接创建于 `tasks/review/TASK-035-d13-route-c/`，`Status: REVIEW`。
- **理由：** 状态机要求「状态与目录**两步同时做**」；本任务在**一个交付请求内**完成「实施 → 提交审查」，
  故不存在需要 `ACTIVE` 状态的版本控制时点。若强行拆成两次提交，只会产生一个**纯噪声**的中间提交。
- **代价与披露：** 这使 TASK-035 在版本历史中**没有 `ACTIVE` 快照** —— 如实登记。

### D3 · 能力记录 §7 **就地标记 ✅**，而**不重排编号**

- **理由：** §7 的项目编号被**多处交叉引用** —— TASK-033 的 `Known Issues` 10 / 11 与
  `handoffs/2026-10-15-archive-review.md` 均引用「**§7 第 3 项**」。**重排会静默破坏这些引用**，
  而那正是本任务要消除的**失真**类别。
- **代价：** 「未决与待办」表中将出现已闭环的行。**这是刻意的取舍**：可读性让位于**引用完整性**。

### D4 · `.agents/**` **不在版本控制内** ⇒ 只能直接更新（**本任务最大的局限，特此披露**）

- **事实（2026-10-15 实测）：** `git rev-parse --show-toplevel` 在 `E:/NDLDSN-WORKSPACE` 返回
  `fatal: not a git repository`；`git ls-files | grep -c '^\.agents/'` = **0**。
  即 `.agents/**`（规则 / 协议 / 设计方案）**既不在本仓库、也不在任何 Git 仓库内**（D9 尚未落地）。
- **后果：** ① 本任务的**规范本体**（R1–R3）**没有版本历史、不经审查、不产生 CI 证据**；
  ② 本交付请求**只能覆盖仓库侧**（R4–R8）。
- **处置：** **如实披露**，并把该局限**登记为 `Known Issues` 2**；
  它同时构成对 **D9**（`.agents/` 纳入 Git）的**新的现实依据**。
