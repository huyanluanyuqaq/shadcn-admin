## 4. 整改项

> 编号 `R#` 为**审查整改编号**，与 `TASK-052` 档案正文里的「R1 校验 / R2 兜底」不是同一体系。

### R1 — 【阻断合并 · 代码】邮箱大小写变体绕过「一条订阅一个邮箱」，静默产生同一订阅两条绑定

**复现（我自己的探针 F，非档案断言）**：对**同一条**订阅先后同步 `a@x.com` 与 `A@X.COM`：

```
F. 同订阅先后用 a@x.com / A@X.COM 同步 → 200 / 200；绑定行数=2；邮箱=["a@x.com","A@X.COM"]
```

**成因（自相矛盾的半实现）**：

- 守卫 `resources.ts:596-616` 用 `ne(sql\`lower(${emailBindings.email})\`, email.trim().toLowerCase())`
  ⇒ 大小写不同**视为同一邮箱**，不报 409；
- 随后的 upsert 查找 `resources.ts:624` 用 `eq(emailBindings.email, email)`
  ⇒ 大小写不同**视为不同绑定**，找不到就 `insert`（`resources.ts:666-673`）；
- 表上 `uniqueIndex('uq_email_bindings_email_pool')`（`schema.ts:184`）是 BINARY 比较，挡不住；
  `subscription_id` 只有普通索引（`schema.ts:185`）——「一条订阅一条绑定」本来就靠应用层维持。

**可从正常 UI 触发**：客户编辑只把邮箱大小写改一下（`a@x.com` → `A@X.COM`，链接不变），
前端 R1 用 `toLowerCase()` 比较（`customers-action-dialog.tsx:463-464`）⇒ 判定「邮箱未变」⇒ 放行；
保存后 `syncEmailBinding` 带新大小写 + 同一 `subscriptionId`（同文件 `511-524`）⇒ 服务端新增一条绑定行。
此后该订阅长期挂着两条只有大小写不同的绑定；旧订阅改为未分配并到期满 24h 后，
两条会**同时**以 E4 出现在邮箱管理（`emails-columns.tsx:137-156` 逐行渲染）。

**这正是本任务要根除的「同一订阅两条绑定」形态**，只是换了个维度。

**建议修法（交由实现方定，不代替设计）**：写入前把 `email` 归一化（`trim().toLowerCase()`）
并在 upsert 查找处用 `lower()` 比较；同时对历史行做一次一致性检查
（`SELECT subscription_id, lower(email), COUNT(*) ... GROUP BY 1,2 HAVING COUNT(*)>1`）。
若认为「大小写就是不同邮箱」，则必须把守卫的 `lower()` 去掉——**两者不能一半一半**。

### R2 — 【合并前置 · 文档/注释】旧邮箱记录被称作「仅注册态」，与实现及同文档归属表矛盾

- `docs/technical/api-contract.md:342`：「旧邮箱记录不再被「并入新邮箱」，而是原样保留为**「仅注册态」**」；
- `server/src/routes/resources.ts:558-559` 与 `src/features/customers/components/customers-action-dialog.tsx:508-509` 同措辞。

**实测**：换链接后旧绑定 `subscription_id` **不变**（脚本场景 1「旧邮箱绑定保留且仍指向旧订阅 C」；探针 A 同结论），
因此它**不是** E1（E1 定义是 `subscription_id IS NULL`，见同文档 `api-contract.md:81`），
而是按旧订阅状态落在 E2 或 E4。同文档 81-83 行自己的表就否证了 342 行。

**建议**：改为「原样保留（仍指向旧订阅），归属按 E2/E4 派生；旧订阅到期满 24h 后才重新出现在邮箱管理」。

### 9. 逐条结论

#### 9.1 R1（同步 upsert 定位）— **已闭合**

`git show 074e557` 把 `resources.ts:676` 从 `eq(emailBindings.email, email)` 改为
``eq(sql`lower(${emailBindings.email})`, email.trim().toLowerCase())``，
与守卫（`resources.ts:651`）同口径；落库分支 `resources.ts:719-723` 仍是 `values({ email, ... })`，**未小写化**。

我的探针（A 组，独立于仓库脚本）：

```
A. sync：同订阅 a@x.com → A@X.COM
   status=200/200 rows=1->1 [{"id":1,"email":"a@x.com","pool":1,"sub":1}]
```

- 行数 `1→1`（不是「状态码正常、行数 +1」）；
- 落库值仍是首次的 `a@x.com`，第二次的 `A@X.COM` 没有覆盖它、也没有新增行；
- `pool_id IS NULL` 分支同样闭合：探针 A%（`poolId` 缺省 → null）`rows=1`，落库 `n@x.com`；
  该分支在实现里走 `samePool = (row.poolId ?? null) === poolId`（`resources.ts:678`），null 与 null 相等，与 CRUD 的 `isNull` 分支语义一致。
- 守卫本身没被改坏：探针 E（`e1@x.com` 已挂订阅，再同步 `e2@x.com`）`409`、行数不变；
  探针 F（同订阅已挂 `A@X.COM`，再同步同邮箱变体 `a@x.com` 到另一订阅）`200`、仍 1 行、落库大小写未被改写。

#### 9.2 R4（`/bundle` 判重 ①）— **已闭合**

`resources.ts:472` 同样改成 `lower()` 比较（`pool.id` 恒非空，故 `eq(poolId, pool.id)` 无 NULL 分支，与实现一致）。
探针 B：预置 `(a@x.com, P1)` 后用 `A@X.COM` + 新链接调 bundle：

```
status=409 before={"bindings":1,"pools":1,"subs":0} after={"bindings":1,"pools":1,"subs":0}
```

三表逐一零新增（不只是状态码）。

#### 9.3 R5（`/email-bindings` CRUD 新增 `beforeWrite`）— **主路径已闭合，但仍有两条缺口**

`resources.ts:310-339`：比较 ``sql`lower(email) = lower(输入)` ``、`poolId === null ? isNull : eq`、`id === null ? undefined : ne(id, id)`；
`crud.ts:246`（POST）与 `crud.ts:280`（PATCH）都在写库前调用。

能挡住的部分（探针 C / G）：
- `PATCH b@x.com → A@X.COM`（与既有 `a@x.com` 同供应商）→ `409`，行数 `2→2`，被拦行仍是 `b@x.com`；
- 同邮箱第二条 `pool_id IS NULL` 绑定 → `409`，原行未动；
- 同一行只改自身大小写 → `200`（`ne(id)` 自排除生效）。

缺口见 §11 的 N1 / N2。

#### 9.4 三处入口口径是否一致 — **比较口径一致，覆盖面不一致**

| 入口 | 比较 | NULL 分支 | 落库值 |
|---|---|---|---|
| `sync`（`resources.ts:676`） | `lower(db.email) = 入参 trim+lower` | 内存 `(poolId ?? null) === poolId` | 原样（`721`） |
| `bundle` ①（`resources.ts:472`） | 同上 | 不可达（bundle 必须有供应商） | 原样（`556`） |
| CRUD `beforeWrite`（`resources.ts:331`） | `lower(db.email) = lower(入参 trim)` | `isNull(poolId)` | 原样（`crud.ts:290` 直接 `set(values)`） |

三处都是 `trim` + 大小写不敏感、都不做小写化落库，`pool_id IS NULL` 语义一致（NULL 视为同一个格子）。
**不一致的是覆盖面**：`sync` / `bundle` 无条件判重，CRUD 的 `beforeWrite` 在 `values.email` 不是字符串时**直接 `return null` 放行**
（`resources.ts:311-312`）——这正是 N1 的成因。

#### 9.5 行为变化（NULL 收紧）— **接受，但有一个副作用登记为 N2**

(a) `server/scripts/smoke.ts:981-997` 那条「同一邮箱在未指定供应商下可单独绑定（NULL 互异）」**在现实现下仍然通过**。
按代码推断：该用例前两步只写入了 `(mail<suffix>@example.com, poolId)`（`smoke.ts:952-960`）与一次 409 尝试，
库里**不存在** `pool_id IS NULL` 的同邮箱行，故 `beforeWrite` 的 `isNull` 分支查不到 ← 放行 → `201`。
**但它的注释/用例名（`smoke.ts:984`、`:994`「SQLite 唯一索引视 NULL 互异」）已经过期**：NULL 互异现在只对直接写库成立，
应用层已把同一 `(邮箱, NULL)` 视为一个格子。这条用例**断言仍对、理由已错**，建议改注释（不必改断言）。
注：`smoke.ts` 不在本轮门禁内，且需要起服务，我**没有实际运行它**，此结论是读代码推断。

(b) 是否符合「判定单元 = (邮箱, 供应商)」：**符合**。`(a@x.com, NULL)` 与 `(a@x.com, P1)` 是两个不同单元，
而 `(a@x.com, NULL)` 重复第二次并不会产生新的「身份」，只会在 E1 列表里出现同一邮箱两行；
客户端没有登记供应商时也没有「同一邮箱两个不同供应商」的表达需求。故收紧不误伤正常场景，
反例（跨供应商）实测仍放行：探针 D（sync 跨供应商 200/200 落两行；bundle 同邮箱同供应商仍 409；POST 第三个供应商 201）。

副作用：存量重复行变得难以编辑（N2），这不是收紧 NULL 语义造成的，而是「判重不与自身旧值比较」造成的。

#### 9.6 文档（`docs/technical/api-contract.md:303-309`，主控位直写、未提交）— **有两处失真**

逐句核对：

| 文档声称 | 实现 | 判定 |

| 「`POST`/`PATCH /email-bindings` 另有一层 `beforeWrite` 校验」 | 有，但**仅在请求体带 `email` 时**才判重（`resources.ts:311-312`） | **夸大**（N1） |

| 「落库值保留原样大小写、不做小写化、不改写存量」 | 三处落库均为入参原样；无 migration | 成立 |

### 11. 新发现

#### N1 — 【代码 · 非阻断（当前 UI 不可达）】`PATCH` 不带 `email` 时完全跳过判重，仍能造出同供应商大小写重复

`resources.ts:311-312`：`values.email` 非字符串即 `return null`。所以「只改 `poolId`」的 PATCH 绕过了整个校验。

我的探针 C'（真实路由，真实库）：

```
reset → 预置 (a@x.com, P1) 与 (A@X.COM, P2)
PATCH /email-bindings/{第二行} {"poolId": P1}
   status=200 rows=2->2 p1 下同邮箱行数=2 [{"email":"a@x.com","pool":5},{"email":"A@X.COM","pool":5}]
```

唯一索引 `uq_email_bindings_email_pool` 是 BINARY 比较，挡不住 → **同一供应商下出现同一邮箱的两条绑定**，
与本轮要闭合的缺陷同形态，只是换成了「改供应商」这个动作。

可达性：我 grep 了全部前端调用点，`useUpdateEmailBinding` 只在 `emails-action-dialog.tsx:204` 使用，
而该对话框提交的是**全量 5 字段**（`emails-action-dialog.tsx:259-266`，含 `email`），
故**当前 UI 不会触发**；`docs/technical/api-contract.md:303` 的「POST/PATCH 另有一层校验」因此对 PATCH 是**夸大**，
对这一形状应加一句限定，或让 `beforeWrite` 在 `email` 缺失时用库中现值补全后再判重（与它已经为 `poolId` 做的事对称）。

#### N2 — 【行为 · 非阻断】存量重复行经 UI「编辑」保存后恒 409，与「只阻止新引入的重复」相矛盾

`beforeWrite` 只排除自身 id，不与「本行原来的 (email, pool)」比较；因此只要库里已存在上一轮缺陷留下的
`(a@x.com, P1)` + `(A@X.COM, P1)`，通过 UI 编辑第二行（全量提交，email 未改，只改 status/remark）会命中第一行 →

```
全量 PATCH status=409 message="该邮箱已绑定同一供应商下的订阅，请直接编辑已有绑定"
只传 status 的部分 PATCH → 200
```

即：用户**不动邮箱也保存不了**，只能改用「只传部分字段」的调用（UI 不提供）或删行。
`docs/technical/api-contract.md:307`「不改写存量」与上一轮客户表口径「不动 email 就照常保存」在这种行上不成立。
这些行恰恰是上一轮 R1 缺陷的产物，真实库里存在的概率不低（我未读生产库，无法统计，见 §12）。
建议：`beforeWrite` 先取本行现值，若 `(lower(email), poolId)` 与现值相同则跳过判重（等价于「只在改变身份时才判重」）。

#### N3 — 【文档 · 合并前置】`api-contract.md:301-302` 与 `:308` 自相矛盾

旧句「同邮箱 + 未指定供应商均为合法的新身份（SQLite 唯一索引视 NULL 互异）」是**改动前**的事实，
本轮把「两条 NULL 绑定」收紧为 409 后未回改，同一小节内前后打架。建议把旧句改成
「同邮箱 + 未指定供应商是**另一个**身份（只有一条）；第二条 NULL 绑定由应用层 409 挡下」。

#### N4 — 【文档/注释 · 非阻断】`smoke.ts:984`、`:994` 的理由已过期

见 §9.5(a)：断言仍会通过（我按代码推断，未运行），但「NULL 互异」不再是应用层的实际行为。
