## 4. 整改项

> 编号 `R#` 为**审查整改编号**，与档案「场景与规则」里的「R1 校验 / R2 兜底」不是同一体系。

### R1 — 【合并前置 · 档案/文档】「旧邮箱 B 显示未分配」这一句在当前的归属模型下不成立

- 档案出处：`TASK.md:101`（S1 表格「邮箱管理」列）、`TASK.md:167`（AC-7 正文）、`TASK.md:181`（TASK-053 注记称「仍然成立」）。
- 代码与文档还有两处同口径措辞：`docs/technical/api-contract.md:342`、`server/src/routes/resources.ts:558-559`
  ——把旧邮箱记录称作「**仅注册态**」，而「仅注册」的定义是 `subscription_id IS NULL`（`api-contract.md:81`）。

**实测（探针 A，仓库外脚本，真实路由 + 真实迁移的临时库）**：

```
A. sync=200; 列表=[] total=0
A. 库中 B 行仍存在=true 指向订阅=1（应为 1）
A. 旧邮箱 B 出现在邮箱管理列表=false
```

即：换链接后 B 的绑定行确实原样保留、仍指向 C（这一半成立），但 C 仍是「有订阅、无客户、未到期」的
E2 ⇒ 按 `resources.ts:311-330` 的归属条件**不进入邮箱管理**；只有当 C 自身到期满 24h 变成 E4，
B 才会以「未分配」出现在邮箱管理。**「邮箱管理显示「未分配」」在 S1 的常规时点不成立。**

**定性**：这不是本轮代码缺陷（代码符合 TASK-053 的裁决模型），是**档案文字未同步**
（`TASK-052` 的 S1 表与 `TASK-053` 注记都写早了）。整改对象是档案与文档措辞，不是 `resources.ts` 逻辑。

**建议**：`TASK.md:181` 改为「AC-7 的**落库形态**仍然成立；「显示未分配」已由 TASK-053 的归属模型取代——
旧订阅未到期时 B 行不显示在邮箱管理，到期满 24h 后以 E4 出现」；`api-contract.md:342` 与两处代码注释同步
（「仅注册态」→「原样保留、按 E2/E4 派生」）。
