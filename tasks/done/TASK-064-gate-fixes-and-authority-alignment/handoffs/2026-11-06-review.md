## 3. 专项核查

### 3.1 A14 能否真的检出「审计脚本自身漂移」——分四种情形

| 情形 | 实测结果 | 能否检出 |
|---|---|---|
| ① 项目侧单方面 1 字节漂移（第 201 字节取反） | `[FAIL] A14 …不一致（同步会覆盖门禁自身）` | ✅ 能（AC-2 探针成立） |
| ② 纯 CRLF 行尾差异 | `[PASS] A14 …内容一致（行尾已归一化）` | ✅ 按设计豁免 |
| ③ 中央仓不可达（CI 单仓 checkout） | `[WARN] A14 …Standalone 限制` | ❌ 不强制（档案 Known Issues #1 已如实登记） |
| ④ 同步动作执行后 / 针对 A14 自身篡改 | 见下 | ❌ **不能** |

**④ 的实测（隔离探针台，两侧脚本同时置为中央 `7c0e49b` 旧版）：**
```
rolled-back results: A1..A13 全部 PASS/WARN，FAIL=0，exit=0
  -> A14 present = False | A6 = ['WARN']（generic secret key 模式已不在 HARD）
同一棵树用 PR 头新脚本检查：A6=FAIL，A10=PASS，A14=PASS
```
即：R-2 的原始风险（「跑一次同步即把已修正的密钥门禁静默改回 WARN」）**在回退完成后无任何检查报警**。原因有二：同步是 `shutil.copy2` 全量覆盖，**检查逻辑本身就在被覆盖的文件里**；且 A14 只判断「两仓是否相等」，**不判断哪一侧符合已批准的门禁基线**。

**自篡改探针**（改项目侧脚本后重新加载）：
```
从 CHECKS 移除 a14_script_consistency -> 结果中无 A14，FAIL=0，exit=0
把 A14 的 FAIL 分支改为恒真      -> 即使中央侧真实漂移，A14 仍 PASS
```

**结论**：A14 的真实能力边界应表述为「**检出项目侧与中央工作树之间的字节不一致**」，不是「消除同步回退风险」。这是自引用检查的固有边界，非编码错误；要真正闭合 R-2，需一个**不随同步被覆盖的外部锚点**（例如 CI 侧独立哈希校验或把已批准基线的哈希写入受保护文件），并按 `AGENTS.md` §14.1 的「先在默认分支落地作业、再加入必需检查」顺序推进。此项须由主控位/人类裁决，本记录不代为设计。
