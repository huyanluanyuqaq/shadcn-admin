# 公共规范 · 协作（Collaboration）

> Agent 协作的唯一权威定义。**技术栈无关、项目无关。**
> 本文件替代了原 8 角色体系、双协作位模型与 5 个工作流。
> 旧版完整内容见 git tag `pre-consolidation-v1`。

---

## 1. 三个角色

| 角色 | 职责 | 明确不做 |
|---|---|---|
| **Coordinator（主控）** | 理解需求、定验收标准、判任务规模、拆分、分派、跟踪进度、汇总成果、组织最终验收 | 不写业务代码 |
| **Developer（开发）** | 接收明确任务、读规范、理解模块、在独立分支实现、跑测试、开 PR、说明改动与验证结果 | 不批准自己的交付 |
| **Reviewer（审查）** | 按需启用。检查正确性、潜在缺陷、规范符合度、测试结果、回归风险，给出明确意见 | 不同时担任该任务的 Developer |

**角色是帽子，不是进程。** 一个 Agent 可依次戴多顶帽子；戴帽子 = 读本文件 + 声明角色 + 遵守权限边界。

### 两条不变量（不可被任何层级削弱）

| # | 不变量 | 说明 |
|---|---|---|
| **I1** | 同一时刻一个 Agent 只戴一顶帽子 | 不允许一边实现一边批准自己 |
| **I2** | **实现者 ≠ 批准者** | 审查的价值来自**视角独立**，不是进程独立。换会话、换模型都能达成；**同会话自我确认不能达成** |

> I2 是唯一无法靠"兼任"绕开的约束。若只有 1 个 Agent 且无法开新会话，
> 该任务**不得标记完成**，且必须在任务记录中写明「审查为自我审查，未经独立验证」。

## 2. 任务分级（核心制度）

所有任务按规模分级，**不同级别的产物要求不同**。目的是不让小任务背大文档，也不让大任务缺证据。

| 级别 | 判据（满足任一即升级） | 必需产物 |
|---|---|---|
| **S（小）** | 单模块、无跨模块影响、无破坏性变更、验收标准 ≤ 3 条 | 分支 + PR（PR 描述含验收标准勾选）。**不需要任务目录、不需要交接记录** |
| **M（中）** | 多文件但边界清晰；或涉及测试补充；或验收标准 4–8 条 | 轻量任务文件 + PR |
| **L（大）** | 跨模块；或破坏性变更；或涉及数据迁移；或需独立审查 | 完整任务文件 + 交接记录 + 合并记录 + 独立审查 |

### 任务文件位置

```
projects/<name>/tasks/<state>/<task-id>/
├── TASK.md          # 任务定义 + 当前状态（M/L 级才有）
└── handoffs/        # 仅 L 级需要
```

`<task-id>` 格式：`TASK-<三位序号>-<短横线slug>`，如 `TASK-012-user-login`。

### 状态目录（4 个，粗粒度）

```
tasks/backlog/  →  tasks/active/  →  tasks/review/  →  tasks/done/
```

逻辑状态记录在任务文件的 `Status` 字段，**不额外建目录**：

| 状态 | 所属目录 |
|---|---|
| `BACKLOG` / `READY` | `backlog/` |
| `ACTIVE` / `BLOCKED` | `active/` |
| `REVIEW` / `CHANGES_REQUESTED` | `review/` |
| `DONE` | `done/` |

> 仅 `BACKLOG ↔ READY`、`ACTIVE ↔ BLOCKED` 之间切换时目录不动，只改 `Status`。

## 3. 任务拆分规则

**只有同时满足以下全部条件才并行拆分：**

- 子任务有相对独立的交付结果
- 可以明确划分模块或文件边界
- 子任务之间不存在强依赖
- 并行确实能缩短整体时间

**否则串行执行。** 并行度受耦合度限制，不受 Agent 数量限制。宁少勿多。

- 每个任务有且只有一个负责人
- 不同 Agent 不同时修改同一文件
- 存在强依赖 → 按顺序执行，不强行并行

---

## 4. 并行协作的四个轻量机制

不使用锁文件、数据库、调度器。

| 机制 | 做法 |
|---|---|
| **任务所有权** | 一个任务同一时刻只有一个负责人；领取时在任务文件写 `Owner` 与时间；已被占用 → 不要抢，换一个 |
| **文件范围** | 每个任务声明 `File Scope`（允许改动的路径）；不同任务的文件范围不应重叠 |
| **分支隔离** | 一个任务一个分支，命名见 `git.md` |
| **状态可见** | 任务文件的 `Status` 字段表达占用状态 |

## 5. 交接记录（轻量化）

### 什么时候必须写

| 情形 | 是否必须 |
|---|---|
| 跨 Agent 交接 | ✅ 必须 |
| 跨会话交接（含换模型） | ✅ 必须 |
| Agent 即将退出且任务未完成 | ✅ 必须 |
| 同一 Agent 在同一会话内串行推进 | ❌ 不必须，在任务文件记一行即可 |
| S 级任务 | ❌ 不需要 |

### 放在哪

任务目录内：`tasks/<state>/<task-id>/handoffs/`。任务自包含，随归档整体移动。

### 命名

```
HANDOFF-<seq>-<from>-to-<to>.md      # 交接记录，seq 三位递增
YYYY-MM-DD-review.md                 # 独立审查记录（新会话出具）
YYYY-MM-DD-<scope>-review.md         # 同任务多份独立审查时用 scope 区分
```

- 审查记录日期用**出具结论的日期**
- **不加轮次序号**（不用 `review2.md`）
- 文件首行标题必须含任务号

### 内容要求

必须包含：From / To / Task / Date / Current State / Completed Work / Changed Files / Tests / Known Issues / Remaining Work / Assumptions / Risks / Next Action。

**具体、可执行、诚实、自包含。** 禁止空泛描述（"完成了相关工作"）、禁止遗漏已知问题（无则写"无"）、禁止 `Next Action` 写成"继续"。

## 6. 执行流程

```
需求输入
   ↓
Coordinator 分析需求，判定规模（S/M/L）
   ↓
   ├─ S → 指派一个 Developer 直接做
   └─ M/L → 判定是否拆分（见 §3）
   ↓
Developer 独立开发（独立分支）
   ↓
提交代码 + 开 PR
   ↓
   ├─ S/M → Coordinator 核对验收标准
   └─ L → 独立 Review（I2）
   ↓
Coordinator 检查整体结果 → 集成、测试、验收
   ↓
完成
```

## 7. 明确不做

为避免过度设计，本框架**刻意不引入**：

- ❌ 为每种工作设立固定 Agent / 独立进程 / 独立模型
- ❌ 角色调度器 / 编排器
- ❌ 锁文件 / 分布式锁 / 消息队列
- ❌ 与 Git 平台重复的复杂任务状态管理系统
- ❌ 要求每个小任务生成大量任务文档与交接文档

> 协作靠「任务文件 + 分支 + Owner 字段」已足够，且完全透明、可调试、无额外依赖。
