# 公共规范 · 质量（Quality）

> 合并自原 `coding.md` / `testing.md` / `security.md` / `documentation.md` 四篇。
> **技术栈无关。** 项目可在 `AGENTS.md` 中补充或覆盖非受保护部分。

---

# 一、代码质量

## 1. 最小改动

- 只改完成任务所需的最小范围。
- **禁止顺带重构**：无关的格式化、重命名、结构调整另开任务。
- 改动越大，Review 成本与风险越高。

## 2. 可读性优先

- 命名表达意图：`calculateTax()` 而非 `calc()`。
- 函数单一职责；过长应拆分。
- 避免深层嵌套，优先早返回（early return）。
- 写"显然正确"的代码，不写"聪明"的代码。

## 3. 显式优于隐式

- 不依赖隐式类型转换、隐式全局状态、隐式副作用。
- 错误必须显式处理，不得静默吞掉。
- 边界条件必须显式处理（空值、空集合、越界、超时）。

## 4. 无魔法值

数字、字符串常量必须命名或提取为配置。例外：`0`、`1`、空字符串等自明值。

## 5. 错误处理

- 区分**可恢复**与**不可恢复**错误。
- 不吞异常：要么处理，要么传播，要么显式记录。
- 错误信息必须包含足够上下文（做了什么、输入是什么、期望是什么）。

## 6. 依赖管理

- 引入新依赖前必须说明理由；优先用已有依赖或标准库。
- 不引入未经审查的依赖（供应链风险）。
- 锁定依赖版本，使用锁文件。

## 7. 注释与文档

- 注释解释**为什么**，不是**是什么**。
- 公共接口必须有文档注释（用途、参数、返回、异常）。
- 过时注释必须删除或更新。
- 不保留注释掉的代码块 —— 版本控制会记住历史。

## 8. 一致性

- 遵循项目已有的风格与结构。
- 项目无明确风格时，遵循该语言社区主流规范。
- 格式化工具必须通过。

## 9. 禁止事项（部分为受保护）

| 禁止 | 原因 |
|---|---|
| 硬编码密钥 / 令牌 / 密码 | 🔴 安全（受保护） |
| 关闭安全检查以"让代码跑通" | 🔴 削弱受保护规则 |
| 吞掉异常 | 掩盖缺陷 |
| 复制粘贴大段逻辑 | 维护成本 |
| 提交调试代码 / 打印语句 | 污染 |
| 提交未使用的依赖 | 供应链风险 |

# 二、测试

## 1. 基本原则

- **测试验证行为，不验证实现细节。** 重构内部结构不应导致测试失败。
- **必须确定性**：同一输入同一结果；禁止依赖时间、随机、网络、执行顺序。
- **必须独立**：任一测试可单独运行，无顺序依赖。
- **必须快速反馈**：慢测试隔离为集成/端到端。

## 2. 测试层次

| 层次 | 范围 | 速度 |
|---|---|---|
| Unit | 单个函数/类 | 快 |
| Integration | 模块间协作 | 中 |
| Contract | 对外接口 | 中 |
| End-to-End | 完整流程 | 慢 |

**测试金字塔：** Unit 占多数，E2E 占少数。

## 3. 必须覆盖的情形

每个被测试的行为至少覆盖：

- **正常路径**
- **边界条件**（空、零、最大/最小、单元素、多元素）
- **异常路径**（非法输入、缺失依赖、超时、并发冲突）
- **回归点**（曾经出过问题的地方必须有测试守护）

## 4. 命名与结构

命名描述**被测行为与预期**：

```
✅ test_rejects_login_when_password_is_expired()
✅ should return empty list when no items match filter
❌ test1()   ❌ testLogin()
```

推荐 Arrange–Act–Assert 三段式。一个测试只断言一个行为。测试代码的可读性标准与产品代码相同。

## 5. 🔴 禁止事项（受保护规则，任何层级不得放宽）

| 禁止 | 原因 |
|---|---|
| 为了通过而删除 / 跳过测试 | 掩盖缺陷 |
| 弱化断言（如断言恒真） | 测试失去意义 |
| 依赖真实外部服务 | 不确定性 |
| 测试之间共享可变状态 | 顺序依赖 |
| 依赖 `sleep` 等待异步 | 脆弱、缓慢 |
| 用"测试暂时不可用"规避失败而不记录 | 掩盖缺陷 |

# 三、安全

## 1. 默认安全姿态

| 维度 | 默认值 |
|---|---|
| 访问控制 | 拒绝 |
| 输入 | 不可信 |
| 数据 | 加密 |
| 日志 | 脱敏 |
| 依赖 | 锁定并扫描 |
| 权限 | 最小 |
| 失败 | **关闭（fail-closed）**，不失败开放 |

## 2. 输入与注入

- 所有外部输入必须校验。
- **禁止**将未校验的输入拼接进查询、命令、路径、模板。

## 3. 认证与授权

- 认证（你是谁）与授权（你能做什么）必须分离。
- 每个受保护操作都必须校验授权，不得依赖前端隐藏。
- 会话/令牌必须有合理的过期与失效机制。

## 4. 依赖与供应链

- 引入依赖前评估：维护状态、已知漏洞、许可证、体积。
- 锁定版本；定期更新并扫描已知漏洞。
- 禁止从未知来源安装依赖。

## 5. 数据与日志

- 传输加密（TLS）；敏感数据静态加密；最小化收集与保留。
- 日志**不得**包含凭据、令牌、个人数据。
- 错误信息对外不得泄露内部实现细节（堆栈、路径、版本）。
- 记录安全事件（登录失败、权限拒绝、异常访问）。

## 6. 高风险操作

删除数据、数据库迁移、修改生产环境、修改安全策略、修改基础设施、大规模重构、
破坏性 Git 操作 —— 必须走 `change-safety.md`。

## 7. 发现安全问题

1. **立即停止**相关变更
2. 评估影响范围与严重程度
3. 修复前不公开披露细节
4. 修复后验证并记录

## 8. 🔴 覆盖规则（受保护）

- ✅ 项目可以**增强**
- ❌ 项目**不得削弱**本文件任何安全约束
- ⚠️ 修改本文件安全部分需 **Security 视角 + 人类**双重批准

# 四、文档

## 1. 文档即事实来源

- **单一事实来源**：一条信息只在一处定义，其他位置引用而非复制。
- 文档过时比没有文档更危险 —— 必须与代码同步更新。

## 2. 文档层级

| 层级 | 位置 |
|---|---|
| 需求 | `docs/requirements/` |
| 架构 | `docs/architecture/` |
| 技术 | `docs/technical/` |
| 决策 | `docs/decisions/`（ADR） |
| 运维 | `docs/operations/` |

## 3. 写作原则

- **结论先行**，再给理由。
- **面向读者**：假设读者不了解上下文。
- **具体可执行**：不写"应该注意性能"，写"当 QPS > 1000 时 X 成为瓶颈，建议 Y"。
- **简洁**：能一句话说清不用三段。
- **示例优于描述**。

## 4. 必须更新的时机

| 变更类型 | 必须更新 |
|---|---|
| 新增/修改接口 | `docs/architecture/` 或 `docs/technical/` |
| 改变数据模型 | `docs/architecture/` |
| 重要技术决策 | 新建 ADR |
| 修改部署方式 | `docs/operations/` |
| 修改需求/验收标准 | `docs/requirements/` |
| 新增依赖 | `docs/technical/` |

## 5. ADR 触发条件

- 引入或替换核心依赖 / 框架 / 数据库
- 改变系统架构（分层、模块边界、通信方式）
- 选择有长期影响的方案且存在合理替代
- 接受重要技术债
- 推翻先前的 ADR

## 6. 格式

- Markdown；文件名小写 + 连字符（`payment-flow.md`）。
- 每文件仅一个 `#` 顶层标题。
- 代码块标注语言；用相对路径链接其他文档（保证可移植）。

## 7. 🔴 禁止事项（安全相关为受保护）

| 禁止 | 原因 |
|---|---|
| 文档中包含密钥/凭据 | 🔴 安全（受保护） |
| 复制粘贴而非引用 | 破坏单一事实来源 |
| 保留过时文档而不标注 | 误导 |
| 用 TODO 占位交付 | 不完整 |
| 无来源的断言 | 不可验证 |

## 8. 文档与代码同源

- 文档变更与代码变更应在**同一任务**内完成。
- Reviewer 须检查文档是否同步。
- 接口文档优先由代码生成，避免手工漂移。
