# Rule: Testing

> 通用测试规范。**技术栈无关。**

---

## 1. 基本原则

- **测试验证行为，不验证实现细节。** 重构内部结构不应导致测试失败。
- **测试必须确定性。** 同一输入必须产生同一结果；禁止依赖时间、随机、网络、执行顺序。
- **测试必须独立。** 任一测试可单独运行；测试之间无顺序依赖。
- **测试必须快速反馈。** 慢测试应被隔离（标记为集成/端到端）。

## 2. 测试层次

| 层次 | 范围 | 目标 | 速度 |
|------|------|------|------|
| Unit | 单个函数/类 | 逻辑正确性 | 快 |
| Integration | 模块间协作 | 接口契约 | 中 |
| Contract | 对外接口 | 兼容性 | 中 |
| End-to-End | 完整流程 | 用户场景 | 慢 |

**测试金字塔：** Unit 应占多数，E2E 应占少数。

## 3. 必须覆盖的情形

每个被测试的行为至少覆盖：

- **正常路径**（Happy path）
- **边界条件**（空、零、最大值、最小值、单元素、多元素）
- **异常路径**（非法输入、缺失依赖、超时、并发冲突）
- **回归点**（曾经出过问题的地方，必须有测试守护）

## 4. 测试命名

命名必须描述**被测行为与预期**：

```
✅ 正确：test_rejects_login_when_password_is_expired()
✅ 正确：should return empty list when no items match filter
❌ 错误：test1()
❌ 错误：testLogin()
```

## 5. 测试结构

推荐 Arrange–Act–Assert（三段式）：

```
Arrange: 准备输入与依赖
Act:     执行被测行为
Assert:  验证结果
```

- 一个测试只断言**一个行为**（可有多个断言，但针对同一行为）。
- 测试代码的可读性标准与产品代码相同。

## 6. 禁止事项

| 禁止 | 原因 |
|------|------|
| 为了通过而删除/跳过测试 | 掩盖缺陷 |
| 弱化断言（如断言恒真） | 测试失去意义 |
| 依赖真实外部服务 | 不确定性 |
| 测试之间共享可变状态 | 顺序依赖 |
| 依赖 `sleep` 等待异步 | 脆弱、缓慢 |
| 断言日志文本 | 与实现耦合 |
| 把"未测试"报告为"通过" | 虚假信心 |

## 7. 缺陷修复必须附带测试

每个 bugfix 必须新增一个**能在修复前失败、修复后通过**的测试。

## 8. 无测试的情形

若某变更确实无法测试（如纯文档、纯配置），必须在 Handoff 中**显式说明原因**，
并说明人工验证方式。不得静默省略。

## 9. 测试可运行性

- 测试必须能通过**一条明确命令**运行。
- 该命令记录在项目 `AGENTS.md` 的 Testing Commands 中。
- 测试失败必须给出**可定位**的输出（期望 vs 实际）。

---

## 与项目规则的关系

项目在 `AGENTS.md` 中定义：测试框架、测试命令、覆盖率要求、测试目录结构。
**第 6 节的禁止事项属于受保护约束，不可被项目覆盖。**
