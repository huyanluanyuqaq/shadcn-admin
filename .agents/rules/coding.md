# Rule: Coding

> 通用编码规则。**技术栈无关。** 项目可在 `AGENTS.md` 中补充或覆盖非受保护部分。

---

## 1. 最小改动原则

- 只改完成任务所需的最小范围。
- **禁止顺带重构**：无关的格式化、重命名、结构调整应另开 Task。
- 改动越大，Review 成本越高，风险越高。

## 2. 可读性优先

- 命名必须表达意图：`calculateTax()` 而非 `calc()`、`doStuff()`。
- 函数保持单一职责；过长函数应拆分。
- 避免深层嵌套；优先用早返回（early return）降低嵌套。
- 不写"聪明"的代码，写"显然正确"的代码。

## 3. 显式优于隐式

- 不依赖隐式类型转换、隐式全局状态、隐式副作用。
- 错误必须被显式处理，不得静默吞掉。
- 边界条件必须显式处理（空值、空集合、越界、超时）。

## 4. 无魔法值

- 数字、字符串常量必须命名或提取为配置。
- 例外：`0`、`1`、空字符串等自明值。

## 5. 错误处理

- 区分**可恢复错误**与**不可恢复错误**。
- 不吞异常：要么处理，要么传播，要么显式记录。
- 错误信息必须包含足够上下文以便定位（做了什么、输入是什么、期望是什么）。

## 6. 依赖管理

- 引入新依赖前必须说明理由；优先使用已有依赖或标准库。
- 不引入未经审查的依赖（供应链风险，见 `security.md`）。
- 锁定依赖版本。

## 7. 注释与文档

- 注释解释**为什么**，而不是**是什么**（代码本身已说明是什么）。
- 公共接口必须有文档注释（用途、参数、返回、异常）。
- 过时注释必须删除或更新。

## 8. 死代码

- 不保留注释掉的代码块 —— 版本控制会记住历史。
- 删除未使用的导入、变量、函数。

## 9. 一致性

- 遵循项目已有的风格与结构。
- 若项目无明确风格，遵循该语言社区的主流规范。
- 格式化工具（如适用）必须通过。

## 10. 禁止事项

| 禁止 | 原因 |
|------|------|
| 硬编码密钥 / 令牌 / 密码 | 安全风险（受保护规则） |
| 关闭安全检查以"让代码跑通" | 削弱受保护规则 |
| 吞掉异常 | 掩盖缺陷 |
| 复制粘贴大段逻辑 | 维护成本 |
| 提交调试代码 / 打印语句 | 污染 |
| 提交未使用的依赖 | 供应链风险 |

---

## 与项目规则的关系

项目可在 `AGENTS.md` 的 "Project-specific Rules" 中：

- **补充**：增加技术栈相关约定（如"使用 X 框架的 Y 模式"）。
- **覆盖**：在非受保护范围内调整本规则（如缩进风格）。
- **不得覆盖**：涉及安全与系统约束的条目（受保护规则）。
