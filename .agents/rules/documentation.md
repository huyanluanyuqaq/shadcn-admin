# Rule: Documentation

> 通用文档规范。**技术栈无关。**

---

## 1. 文档即事实来源

- 文档不是"额外工作"，而是协作的基础设施。
- **单一事实来源**：一条信息只在一处定义，其他位置引用。
- 文档过时比没有文档更危险 —— 必须与代码同步更新。

## 2. 文档层级

| 层级 | 位置 | 内容 |
|------|------|------|
| 需求 | `docs/requirements/` | 目标、用户、场景、验收标准 |
| 架构 | `docs/architecture/` | 系统结构、模块边界、接口契约 |
| 技术 | `docs/technical/` | 实现细节、算法、配置说明 |
| 决策 | `docs/decisions/` | ADR —— 架构决策记录 |
| 运维 | `docs/operations/` | 部署、监控、故障处理 |

## 3. 写作原则

- **结论先行**：先给结论，再给理由。
- **面向读者**：假设读者不了解上下文。
- **具体可执行**：避免"应该注意性能"这类空话；写"当 QPS > 1000 时，X 会成为瓶颈，建议 Y"。
- **简洁**：能用一句话说清，不用三段。
- **示例优于描述**：能举例就举例。

## 4. 必须更新的时机

| 变更类型 | 必须更新 |
|----------|---------|
| 新增/修改接口 | `docs/architecture/` 或 `docs/technical/` |
| 改变数据模型 | `docs/architecture/` |
| 重要技术决策 | 新建 ADR（`docs/decisions/`） |
| 修改部署方式 | `docs/operations/` |
| 修改需求/验收标准 | `docs/requirements/` |
| 新增依赖 | `docs/technical/` |

## 5. ADR 触发条件

以下情况**必须**创建 ADR：

- 引入或替换核心依赖 / 框架 / 数据库
- 改变系统架构（分层、模块边界、通信方式）
- 选择有长期影响的方案（且存在合理替代方案）
- 接受一项重要的技术债
- 推翻先前的 ADR

模板见 `templates/adr/ADR.md`，存放于 `docs/decisions/ADR-NNN.md`。

## 6. 文档格式

- 使用 Markdown。
- 文件命名：小写 + 连字符（`payment-flow.md`）。
- 顶层标题使用 `#`，且每文件仅一个。
- 代码块标注语言。
- 相对路径链接其他文档（保证可移植）。

## 7. 禁止事项

| 禁止 | 原因 |
|------|------|
| 文档中包含密钥/凭据 | 安全风险（受保护规则） |
| 复制粘贴而非引用 | 破坏单一事实来源 |
| 保留过时文档而不标注 | 误导 |
| 用 TODO 占位交付 | 不完整 |
| 无来源的断言 | 不可验证 |

## 8. 文档与代码同源

- 文档变更与代码变更应在**同一 Task** 内完成。
- Reviewer 在 Review 时须检查文档是否同步。
- 接口文档优先由代码生成（如适用），避免手工维护漂移。

---

## 与项目规则的关系

项目在 `AGENTS.md` 中定义文档的具体位置与额外要求。
**第 7 节中涉及安全的禁止事项属于受保护规则。**
