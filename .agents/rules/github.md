# Rule: GitHub Collaboration

> GitHub 平台上的协作规则。**技术栈无关。**
>
> **本规则不重复 `git.md` 的内容。** 分支命名与提交信息以 `git.md` 为准；
> 本规则只规定**平台协作层**的强制要求。
>
> 详细流程见 `../protocols/github-collaboration.md`；
> 平台实际能强制什么见 `../protocols/github-capability-matrix.md`。

---

## 1. 适用范围

适用于以 GitHub 为协作载体的项目。

**前提：** 项目必须在 `AGENTS.md` 中声明是否启用本规则，并提供自己的**平台能力记录**。
未提供能力记录的项目，不得声称已具备平台门禁。

---

## 2. 分支

- 命名规则见 `git.md` §1。
- 工作分支**必须从最新的默认分支派生**。
- 工作分支**必须推送到远端**（防止仅存于本地而丢失）。
- 一个任务一个分支；一个分支只服务一个任务。
  - **豁免（D13-C，2026-10-15）：** 该分支**同时承载「上一个任务的归档回写」**（§6 的强制要求）。
    这是**刻意的、有界的**例外 —— 范围**仅限 `tasks/**` 的档案与交接记录**，不得借此夹带其它内容。

---

## 3. 提交

- 提交信息格式见 `git.md` §2。
- 每个提交的 footer **必须**包含任务引用（如 `Refs: <task-id>`）。
- 合并前的提交历史**不得**包含调试残留、密钥或无关重构（见 `git.md` §3 / §4）。

---

## 4. 交付请求（Pull Request）

- **所有对默认分支的改动必须通过交付请求合并，禁止直接推送默认分支。**
- 交付请求**必须**关联任务标识。
- 实施期间建议使用草稿状态，自测完成后再标记为可审查。
- 描述内容由**层 1 文件渲染**（字段映射见 `../protocols/github-collaboration.md` §6）。
  **不得只在交付请求里写信息而不回写任务文件。**
- 未建立任务记录（层 1 缺失）时，**不得**创建交付请求。
- 模板：`templates/github/PULL_REQUEST_TEMPLATE.md`。

---

## 5. 检查

- 只有**稳定且必要**的检查才设为必需检查。
- 必需检查**必须包含**（项目可按技术栈增补）：

  | 类别 | 要求 |
  |------|------|
  | 静态检查 | 必须 |
  | 格式检查 | 必须 |
  | 测试 | 必须 |
  | 构建 | 必须 |

- 检查**必须在合并之前运行**；若检查仅在合并后触发，则**不构成门禁**，
  项目必须在能力记录中如实标注。
- 检查运行标识与结论**必须**记录到任务文件。
- **禁止**通过删除测试、放宽断言、伪造结果或绕过保护规则使检查变绿。

---

## 6. 合并

- 合并前必须满足：审查通过 + 必需检查通过 + 分支保护条件满足 + 必要的授权。
- **默认合并策略：rebase-merge**（保持默认分支线性，同时保留可追溯的提交粒度）。
- 合并后删除该工作分支。
- 合并后**必须**回写任务文件：状态、合并标识、检查运行标识、遗留问题。
  - **★ 回写路径（D13 裁决 · 2026-10-15 · 选项 C）：** 上述回写**并入下一个任务的交付请求**，
    **不单独开「回写专用」交付请求**。因此在下一个任务出现之前，最近完成的任务
    **保持 `Status = REVIEW`、留在 `tasks/review/`**，并须在其 `TASK.md` 中**诚实标注**
    「归档回写待下一个任务补记」。
  - **★ 回归终止（与 §4 的关系）：** §4（禁直推默认分支）与 §6（要求合并后回写）的**无限回归在此终止于深度 1** ——
    由于永不产生「回写专用请求」，任何任务的 `Merge Record` **至多延后一个任务**补记，不会无限套娃。
    （原选项 A「记录分支 + 独立交付请求」成本实测为每任务**多一整套串行审查**，已弃用；选项 B「直推豁免」因与真门禁冲突而失效。详见设计方案 §17.3。）

> **本条的合并策略覆盖 `git.md` §5 的默认值。**
> 理由：rebase-merge 与既有的 fast-forward 习惯一致，且不产生压缩合并造成的证据颗粒度损失。
> `git.md` §5 中「合并前必须 Review PASS + 测试通过」「合并后删除分支」两点**继续有效**。

---

## 7. 禁止操作（含受保护项）

| 操作 | 原因 |
|------|------|
| 直接推送默认分支 | 绕过交付与检查门禁 |
| 对共享分支强制推送 | 覆盖他人工作（同 `git.md` §6） |
| 未经检查覆盖他人分支的修改 | 丢失工作 |
| **由实现者批准自己提交的交付物** | **违反 I2（受保护）** |
| 由 Agent 或自动化自行批准高风险操作 | 绕过人类授权（受保护） |
| 在未获授权时合并、发布或执行破坏性操作 | 越权 |

**绝对禁止：**

- ❌ 提交密钥、令牌、密码、证书
- ❌ 把「未实测的平台配置」描述为已生效
- ❌ 声称平台已强制某项实际未被强制的约定

---

## 8. 平台配置

以下事项**必须**在平台侧单独配置，**不能仅靠提交文件完成**：

- 分支保护 / 规则集（必需 PR、必需检查、禁止强制推送、禁止删除分支、不允许绕过）
- 协作者与权限授予
- 密钥与凭据

配置清单与操作步骤见 `shared/scripts/github_setup_checklist.md`。
配置完成后**必须实测**并记录结论（见 `../protocols/github-capability-matrix.md` §8）。

> **CODEOWNERS 不能单独提供独立审查。** 它只自动请求审查者，
> 不创建独立身份、不启用审批、不阻止合并。

---

## 9. 与项目规则的关系

项目可在其 `AGENTS.md` 中声明：

- 本项目的必需检查清单；
- 本项目的合并策略（覆盖 §6 需注明理由）；
- 本项目的平台能力记录位置。

**下列条目属于受保护约定，项目不得削弱：**

- §4 禁止直接推送默认分支；
- §7 中与 I2（实现者 ≠ 批准者）和人类授权相关的条目；
- §5 中禁止伪造或不正当绕过检查的条目。
