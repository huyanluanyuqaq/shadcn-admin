# Protocol: GitHub Collaboration

> 以 GitHub 为协作载体的端到端流程：任务登记 → 分支隔离 → 实施 → 交付 → 机器验证 → 审查 → 整改 → 合并归档。
> **技术栈无关、项目无关。**
>
> **与其他文件的关系（本协议不重复其内容）：**
>
> | 主题 | 定义位置 |
> |------|---------|
> | 分支命名、提交信息、禁止的 Git 操作 | `../rules/git.md` |
> | GitHub 平台层的强制规则（PR 必需、检查、合并） | `../rules/github.md` |
> | 平台能强制什么、不能强制什么 | `github-capability-matrix.md` |
> | 两个协作位的职责 | `dual-agent-model.md` |
> | 交接的格式与字段 | `handoff.md` |
> | 状态机与目录流转 | `task-lifecycle.md` |
> | 高风险操作的批准流程 | `change-safety.md` |
>
> **适用范围：** 本协议描述 GitHub 平台。其他平台的对应机制需另行定义，**不得直接套用本协议的平台假设**。

---

## 1. 设计前提

1. **GitHub 是协作载体，不是唯一的知识存储位置。** 项目架构、技术规范、安全策略与长期决策
   仍存储在版本控制的文档中。
2. **不得依赖 Agent 的临时对话记忆维持关键任务状态。**
3. **任务状态的唯一事实来源是仓库内的任务文件**，平台侧的记录是其**投影或索引**。
4. **文档制度、平台权限、自动化门禁是三个不同层面**，不得混为一谈
   （见 `github-capability-matrix.md` §1）。

## 2. 三层载体模型

```
┌──────────────────────────────────────────────────────────────────────┐
│ 层 1 · 文件层（唯一事实来源 · 始终可用 · 随仓库版本化）                │
│   tasks/<state>/<task-id>/TASK.md         ← 状态、范围、验收标准       │
│   tasks/<state>/<task-id>/handoffs/**     ← 交接、审查、整改记录        │
│   docs/**                                  ← 架构、规范、ADR、运维      │
│   AGENTS.md                                ← 规则入口与继承             │
│   【性质】可离线 · 独立 clone 后仍完整 · 无平台依赖                     │
└───────────────────────────┬──────────────────────────────────────────┘
                            │ 投影（单向：文件 → 平台；不承载独有事实）
                            ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 层 2 · 平台层（协作与门禁 · 需仓库权限 · 可视与可审计）                │
│   工作分支   ── 隔离边界                                              │
│   提交       ── 变更历史 + 任务引用                                    │
│   PR         ── 交付载体：差异 + 证据 + 审查结论 + 整改轮次            │
│   Actions    ── 机器验证（仅验证，不决策）                             │
│   默认分支   ── 合并落点（受分支保护约束）                             │
│   【性质】在线 · 依赖权限 · 执行门禁 · 不承载不可再生信息              │
└───────────────────────────┬──────────────────────────────────────────┘
                            │ 授权（人类）
                            ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 层 3 · 授权层（人类门禁 · 不可自动化 · 受保护）                        │
│   高风险操作批准（生产 / 迁移 / 密钥 / 权限 / 不可逆）                  │
│   发布授权（含「合并即发布」场景）                                      │
│   规则与权限定义的修改批准                                             │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.1 层间规则（不可违反）

| 规则 | 内容 |
|------|------|
| **L1 自持** | 层 1 不依赖层 2 才能运转。平台不可用（断网 / 无权限）时协作仍可继续 |
| **L1→L2 单向** | 平台状态由文件派生；**禁止**在平台写入文件中不存在的任务事实 |
| **L2 不承载独有事实** | PR 讨论可作为证据，但其**结论必须回写** `handoffs/`，否则跨会话丢失 |
| **L2→L3 需人授权** | Actions 与 Agent **均不得**自行批准层 3 的操作 |
| **L1 缺失即阻断** | 若任务文件不存在 → 该任务**不得**创建 PR（防止无记录变更） |
| **平台不可信为状态源** | 任何「仅存在于平台、未落文件」的信息，视为**不存在** |

## 3. 事实的唯一来源

**不重复维护多套相互独立的状态来源。**

| 事实 | 唯一来源 | 其他位置的角色 |
|------|---------|--------------|
| 任务整体状态 | `TASK.md` 的 Status 字段 | 平台标签 / Issue = 可选投影 |
| 交付与审查状态 | PR 的 Review 状态 + `handoffs/` | 回写后成为层 1 记录 |
| 自动化检查结果 | Actions 的 run | 记录 run 标识到 `TASK.md` |
| 进度总览 | 可选的项目看板 | 只读汇总，非事实来源 |
| 长期技术知识 | `docs/` 中的文档 | — |

## 4. 端到端流程（10 阶段）

| 阶段 | 执行者 | 输入 | 输出（载体） | 进入条件 | 退出条件 |
|------|-------|------|-------------|---------|---------|
| **0 执行前检查** | 主控位 | 需求 | 检查清单 | 需求到达 | 仓库 / 分支 / 工作区状态已确认；工作区**无**未提交变更 |
| **1 需求登记** | 主控位 | 需求 | 任务文件 | 阶段 0 通过 | 背景 / 目标 / 包含范围 / 排除范围 / 验收标准 / 约束 / 依赖 / 风险等级 / 审批要求 / 验证要求 齐全 |
| **2 方案与分配** | 主控位 | 任务文件 | Implementation Plan + File Scope | 查重通过 | 边界明确；依赖满足；必要时获得确认 |
| **3 认领与再检查** | 执行位 | 任务文件 | Owner / Owner Since | 依赖已满足 | 仓库 / 分支 / 工作区 / 规范 / 可行性 / 授权范围 六项已检查 |
| **4 分支隔离** | 执行位 | 任务 ID | 工作分支 | 认领成功 | 分支从最新默认分支派生；**已推送远端**（防本地丢失） |
| **5 实施与提交** | 执行位 | 方案 | 原子提交 + 任务引用 | 分支就绪 | 本地检查全部通过；无调试残留；无密钥 |
| **6 交付请求（PR）** | 执行位 | 分支 | PR（先 Draft） | 分支已推送 | PR 描述包含 §6 的全部字段 |
| **7 机器验证（CI）** | Actions | PR | 检查结论 | PR 创建 / 更新 | 全部必需检查通过；失败须按 §8.3 定性，不得重试掩盖 |
| **8 主控审查** | 主控位 | **实际差异** + 检查结论 | PASS / 需整改 / 需补充说明 | 检查通过 | §5 的 10 项审查范围逐项给出结论 |
| **9 整改与复审** | 执行位 → 主控位 | 审查意见 | 新提交 + 复审结论 | 收到整改要求 | 阻断项关闭且**经复核**（非仅标记已解决） |
| **10 合并与归档** | 主控位 | 门禁全绿 | 合并 + 任务记录回写 | 门禁 + 授权满足 | PR 已合并；任务状态**正确或已按 D13-C 标注「回写待补记」**；文档已更新；遗留问题已有独立记录 |

**关于 Issue：** 本流程**不要求**使用 Issue。任务登记以任务文件为准；
Issue 可作为可选索引（Level 2 自动化），但**不参与状态与审查**。

## 5. 阶段 8 的审查范围（10 项，逐项给出结论）

主控位必须检查**实际的代码差异**，而不是只读 PR 描述。

1. 需求是否满足（**逐条**核对验收标准）
2. 修改范围是否合规（对照 File Scope）
3. 实现是否正确
4. 是否破坏现有架构与接口
5. 是否引入安全或数据风险
6. 测试是否充分（证据是否真实、是否可复现）
7. 文档是否一致（**含否定性断言复核**，见 `../rules/documentation.md`）
8. 是否存在未经批准的重大变更
9. CI 是否满足要求
10. 是否符合完成定义

**审查结论只有三种：** 通过 / 需要整改 / 需要补充说明或验证。
**所有阻断性问题必须有明确整改要求。**

> **独立性要求：** 审查必须由**与实现不同的会话或实例**完成。
> 同一实例的自我确认不等于独立审查（见 `dual-agent-model.md` §5）。

## 6. 交付描述的来源（禁止双写）

PR 描述**不产生新信息**，它是层 1 的渲染。字段来源：

| PR 字段 | 数据来源（层 1） |
|---------|----------------|
| 关联任务 | 任务 ID + 提交 footer 的任务引用 |
| 变更摘要 | 任务文件的 Objective + 变更文件清单 |
| 实现内容与范围 | 任务文件的 Scope / Non-Scope / Implementation Plan |
| 实际测试结果 | 任务文件的验证记录 |
| 未执行的测试及原因 | Handoff 的 Tests + Known Issues |
| 兼容性 / 安全 / 部署影响 | Handoff 的 Assumptions + Risks |
| 回滚方案 | Handoff 的 Risks（回滚段） |
| 遗留问题 | 任务文件的 Known Issues |
| 执行者自检 | Handoff 的交接检查清单 |

**模板：** `templates/github/PULL_REQUEST_TEMPLATE.md`（由模板包分发到各项目）。

> **若某字段在层 1 无对应内容 → 补齐层 1，而不是只写在 PR 里。**

## 7. 机器验证（CI）原则

1. 检查项按项目技术栈选择，**不得假设所有项目使用相同构建工具**。
2. 只有**经过验证、稳定且必要**的检查才应成为强制合并条件。
3. **检查失败必须分析原因**，区分：代码缺陷 / 测试缺陷 / 环境故障 / 依赖故障 / 外部服务故障。
4. **禁止**通过伪造结果、随意删除测试、无限重试或绕过保护规则让检查变绿。
5. 检查的运行标识与结论必须记录到任务文件（见 §10）。
6. **触发时机：** 检查必须在**合并之前**运行，否则无法构成门禁。
   具体触发条件由项目的工作流文件决定，并须在项目能力记录中标注实测结果。

## 8. 异常、冲突与阻塞

### 8.1 文件冲突

两个协作位修改同一文件或模块时：

1. 暂停冲突部分；
2. 保存双方现有修改与相关提交证据；
3. 比较实际差异；
4. 确定**唯一的集成责任位**；
5. 明确合并策略；
6. 解决后重新执行受影响的测试。

**禁止未经检查直接覆盖另一方修改。**

### 8.2 任务重复分配

通过任务记录、分支与交付请求识别重复工作。
**重新分配前必须确认原执行位已停止写入**，或已通过独立工作区与分支完成隔离。

### 8.3 CI 失败

必须区分缺陷类型（见 §7.3），记录实际日志、失败原因与后续处理。
**不得通过无限重试掩盖根因。**

### 8.4 长时间阻塞

阻塞记录必须包含：

- 原因
- 已完成工作
- 当前影响与风险
- 需要的决策或权限
- 恢复条件
- 下一步责任位

### 8.5 方案争议

双方应基于需求、项目规范、实际证据、风险与维护成本提出意见。
主控位负责协调授权范围内的方案选择。
**涉及重大架构取舍、需求变化、不可逆操作或权限边界时，交由人类决策。**

## 9. 合并与归档

满足**审查、检查、分支保护与授权**条件后方可合并。

**★ 回写路径（D13 裁决 · 2026-10-15 · 选项 C）：** 合并后的回写**并入下一个任务的交付请求**，
**不单独开「回写专用」交付请求**（规范来源：`rules/github.md` §6）。因此在下一个任务出现之前：

- 最近完成的任务**保持 `Status = REVIEW` 且留在 `tasks/review/`** ——
  即下面的第 3 项检查在该窗口内**不成立**，这是**已裁决的代价**，不是缺陷；
- 该任务的 `TASK.md` **必须诚实标注**「归档回写待下一个任务补记」；
- §4（禁直推）与 §6（要求回写）的**无限回归终止于深度 1**：任何 `Merge Record` **至多延后一个任务**补记。

合并后，主控位必须确认：

- [ ] 交付请求已正确合并
- [ ] 必需检查符合要求（运行标识已记录）
- [ ] 任务状态与物理目录一致 —— **或**已按 D13-C 标注「回写待补记」（二者必居其一）
- [ ] 必要文档已更新
- [ ] 遗留问题已有独立记录
- [ ] 最终交付报告与实际仓库状态一致
- [ ] 已指明本任务的 `Merge Record` 由**哪一个后续任务**补记（或标注「待补记」）

> **交付请求合并 ≠ 生产部署成功，也不自动等于所有业务验收条件均已满足。**

## 10. 完成定义（补充项）

沿用既有完成标准，并补充：

- [ ] **N1 · 交付留痕完整**：`handoffs/` 含逐条验收标准核对与 PASS/FAIL 结论；
      审查者身份（哪个会话 / 实例）已记录
- [ ] **N2 · 门禁证据可查**：必需检查的运行标识与结论已写入任务文件
- [ ] **N3 · 制度-平台差异披露**：若某项约定**未被平台强制**，已在 `Known Issues` 显式标注
      （最常见的一条：独立审查无平台强制，仅为流程约定）

## 11. 自动化分级

| 级别 | 内容 | 目标 |
|------|------|------|
| **Level 1 · 手动协作** | 人工读任务 → 建分支 → 实施 → 交付 → 机器检查 → 人工审查 → 合并 | 验证制度是否有效 |
| **Level 2 · 半自动** | 任务完整性校验、任务文件 → 平台投影、标签同步、阻塞提醒、报告生成 | 降低重复劳动，**不替代人类审批** |
| **Level 3 · 受控自动执行** | 按任务类型分配、依赖调度、自动触发执行、受控自动合并（仅低风险且条件严格） | 仅在 Level 1 / 2 稳定后 |

**任何级别都不得绕过：** 用户授权、安全约束、质量门禁、高风险操作的人类批准。

**Level 3 的前置条件（未满足前不得启用）：**

- 存在可被平台调用的 Agent 运行时（否则无触发通道）；
- 合并与对外发布已解耦（否则「自动合并」等价于「自动发布」）；
- 已具备分支保护与必需检查。

## 12. 明确不做什么

- ❌ **不依赖 Agent 的对话记忆**维持任务状态。
- ❌ **不重复维护多套状态来源** —— Issue、PR、任务文件三者只允许一个事实来源。
- ❌ **不把平台审批当作独立审查** —— 单身份下平台无法区分两个协作位。
- ❌ **不用重试或删测试掩盖失败**。
- ❌ **不让 Actions 或 Agent 自行批准高风险操作**。
- ❌ **不未经检查覆盖其他实例的修改**。
- ❌ **不在未获授权时执行合并、发布或破坏性操作**。

## 与项目规则的关系

项目可在其 `AGENTS.md` 中声明：

- 本项目的必需检查清单；
- 本项目的合并策略；
- 本项目对平台能力的实测结论（指向项目的平台能力记录）。

**必须遵守：** `../rules/github.md` 中的强制要求；
**不得削弱：** `change-safety.md` 的高风险批准要求、平台能力的如实披露要求。
