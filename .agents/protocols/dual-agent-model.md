# Protocol: Dual-Agent Model

> 双 Agent 协作模型：把「谁协调与验收」和「谁实施与自证」分成两个**协作位（Collaboration Seat）**。
> **技术栈无关、项目无关。**
>
> **与其他文件的关系（本协议不重复其内容）：**
>
> | 主题 | 定义位置 |
> |------|---------|
> | 角色（Role）的职责、家族与分配方案 | `role-assignment.md` |
> | 并行协作的冲突解决 | `collaboration.md` |
> | 角色权限矩阵与通用权限原则 | `permissions.md` |
> | 任务状态机与生命周期 | `task-lifecycle.md` |
> | 交接的格式与时机 | `handoff.md` |
> | 高风险操作的强制流程 | `change-safety.md` |
> | GitHub 平台上的端到端流程 | `github-collaboration.md` |
> | 平台能强制什么、不能强制什么 | `github-capability-matrix.md` |
>
> 本协议只回答一个现有文件未回答的问题：
> **在双 Agent 协作中，两个实例分别对什么负责、各自产出什么证据、在平台侧执行哪些动作。**

---

## 1. 问题

现有框架已定义 8 个角色，并给出「2 个 Agent 最小可行配置」的分配方案（见 `role-assignment.md` §4.1）。
但角色划分回答的是「需要哪些专业职责」，**不回答**下列问题：

1. 谁对「这个任务最终算不算完成」负责？
2. 谁的完成声明可以被采信，谁的不可以？
3. 同一个任务上，两个实例分别向哪个平台载体写入动作？

这三点在协作中一旦含糊，就会出现「双方都以为对方在验收」或「实现者自行宣布通过」。
**双 Agent 模型就是为填补这一层而存在。**

---

## 2. 两个协作位

| 协作位 | 代号 | 定位 | 一句话职责 |
|--------|------|------|-----------|
| **主控位** | Coordinator | 任务协调者与**验收责任人** | 定义「做什么、做完没有」，并对此负责 |
| **执行位** | Implementer | 技术调查者与实施者 | 回答「能不能做、怎么做、实际做了什么」 |

协作位**不是新的角色**，而是角色的**一种分组视角**：

```
        协作位（本协议）                    角色（role-assignment.md）
        ┌───────────────┐                  ┌──────────────────────────────┐
        │   主控位       │  ──映射──→       │ Product · Architect           │
        │  Coordinator  │                  │ Researcher · Reviewer         │
        └───────────────┘                  └──────────────────────────────┘
        ┌───────────────┐                  ┌──────────────────────────────┐
        │   执行位       │  ──映射──→       │ Developer · Tester            │
        │  Implementer  │                  │ Security · DevOps             │
        └───────────────┘                  └──────────────────────────────┘
```

**注意：** 映射是**默认关系**，不是强制绑定。一个实例可以在一生中交替占用两个协作位，
但**在同一 Task 的有效期内不得同时占用两个位**（见 §5）。

---

## 3. 主控位（Coordinator）

主控位是**任务协调者、工作分配者与验收责任人**。

| # | 职责 | 载体 | 证据形态 |
|---|------|------|---------|
| C1 | 理解需求、识别约束、确定验收条件 | `TASK.md` | Acceptance Criteria 条目 |
| C2 | 读取项目规则、检查仓库与工作区状态 | 只读 | 执行前检查清单 |
| C3 | 判断任务类型、风险等级与依赖关系 | `TASK.md` | Risk Level / Dependencies |
| C4 | 登记任务（创建工作单元） | `TASK.md` | 任务目录 + 完整字段 |
| C5 | 制定实施方案并拆分工作项 | `TASK.md` | Implementation Plan + File Scope |
| C6 | 明确执行边界、禁止事项与审批条件 | `TASK.md` | Constraints / Non-Scope |
| C7 | 协调任务认领、并行工作与跨模块依赖 | `TASK.md` Owner + File Scope | Owner 与时间戳 |
| C8 | 审查交付物（读**实际差异**，不读描述） | 代码差异 + 检查结论 | 逐条 AC 核对 + PASS / FAIL |
| C9 | 提出整改要求并**复审**整改结果 | `handoffs/` | 整改项 → 复核结论 |
| C10 | 决定验收状态、整理最终交付报告 | `TASK.md` | Status = `DONE` + Merge Record |
| C11 | 维护架构文档、任务记录与质量规范 | `docs/` | 变更提交 |
| C12 | 对任务管理与验收过程负责 | 证据链 | **不得仅凭执行者的完成声明判定成功** |

**定位约束：** 主控位原则上以分析、协调与审查为主。
**除非明确接管该任务（即转换为执行位并放弃审查资格），不得直接覆盖执行位的代码。**

---

## 4. 执行位（Implementer）

执行位是**技术调查者、实施者与交付材料提供者**。

| # | 职责 | 载体 | 证据形态 |
|---|------|------|---------|
| I1 | 阅读任务说明与相关项目规范 | 只读 | 已读清单 |
| I2 | 检查现有实现、版本控制状态与依赖 | 只读 | 状态输出 / 依赖清单 |
| I3 | 验证实施方案的可行性（不可行即上报） | `handoffs/` | 可行性结论或回退请求 |
| I4 | 在授权范围内创建或使用独立工作分支 | 分支 | 分支名 + 远端存在性确认 |
| I5 | 实施代码、配置、测试与文档修改 | 文件 | 差异 |
| I6 | 执行必要的测试、构建与质量检查 | 检查运行 | **原始输出，而非「已通过」** |
| I7 | 记录实际变更与验证结果 | `TASK.md` + `handoffs/` | 文件清单 + 测试记录 |
| I8 | 提交交付物并提交交接材料 | 平台交付载体 + `handoffs/` | 描述字段齐全 |
| I9 | 根据审查意见整改 | 新提交 | 整改项逐条响应 |
| I10 | 报告方案缺陷、安全风险、范围变化或阻塞 | `handoffs/` + Status | 阻塞记录（五要素） |

**禁止：** 擅自扩大任务范围、覆盖未提交修改、绕过质量门禁、隐瞒失败结果。

---

## 5. 独立性约束

| 编号 | 不变量 | 含义 |
|------|--------|------|
| **I1** | 同一时刻，一个实例只占用一个协作位 | 全部职责串行执行，不得并行声称 |
| **I2** | 实现者 ≠ 批准者 | 实施该变更的实例**不得**批准或验收同一变更 |

**I2 的判定依据是「视角独立」，不是「进程独立」**（与 `role-assignment.md` §4.3 一致）：

- 换会话、换实例、换模型都能达成；
- **同一会话内的自我确认不能达成**。

### 5.1 单实例场景

只有 1 个实例可用时，I1 可以满足（串行），**I2 无法在同一会话内满足**。补救措施：

1. 换一个**全新会话**扮演审查者（不携带实现时的上下文）；
2. 新会话须先读 `TASK.md` + 最新 Handoff，再读实际差异；
3. 若确实无法开新会话，则该 Task 不得标记为 `DONE`，且**必须**在 `TASK.md` 的
   `Known Issues` 中显式记录「审查为自我审查，未经独立验证」。

### 5.2 必须披露的独立性限制

当两个协作位的**平台身份相同**时，平台的审计记录无法区分两个位。
此时必须在项目的平台能力记录中如实标注：

> **「独立审查为流程约定，平台不强制。」**

不得把同一实例的自我检查与独立审查等同描述。详见 `github-capability-matrix.md` §4。

## 6. 两个协作位在平台侧的默认分工

以下为**默认分工**，具体动作的权限由各平台的权限模型决定，
平台实际能强制什么见 `github-capability-matrix.md`。

| 动作 | 主控位 | 执行位 | 强制手段 |
|------|--------|--------|---------|
| 登记任务 | ✅ 独占 | ❌ | 无（约定） |
| 创建/更新任务记录 | ✅ 独占 | ⚠️ 仅更新自身字段 | 无（约定） |
| 创建任务分支 | ❌ | ✅ 独占 | 平台可约束（分支保护） |
| 推送到任务分支 | ❌ | ✅ | 平台可约束 |
| 推送默认分支（合并） | ✅ 独占 | ❌ | **平台可强制**（见下） |
| 提交交付请求（交付载体） | ❌ | ✅ 独占 | 平台可约束 |
| 审查交付物 | ✅ 独占 | ❌ | 约定（单身份下平台不强制） |
| 批准交付物 | ⚠️ 需制度约束 | ❌（平台通常拒绝自批） | **平台可部分强制** |
| 合并 | ✅ 独占 | ❌ | **平台可强制**（必需检查 + 必需 PR） |
| 生产部署 / 迁移 / 密钥 | ❌ | ❌ | **人类授权**（`change-safety.md`） |

> **注：** 「平台可强制」与「平台不强制」的区别是本框架的核心区分之一。
> **不得把文档中的禁止事项误认为平台已经强制限制了该操作。**
> 完整矩阵见 `github-capability-matrix.md`。

## 7. 并行与冲突

两个协作位之间**不建立锁**。冲突通过既有轻量机制解决（详见 `collaboration.md` §2）：

1. **Task Ownership** —— 一个 Task 同一时刻只有一个 Owner；
2. **File Scope** —— 每个 Task 声明允许改动的路径；
3. **工作分支** —— 一个 Task 一个分支，命名见 `../rules/git.md` §1；
4. **Status** —— 通过 `TASK.md` 的 Status 表达占用状态。

**两个协作位不得无协调地同时修改同一文件或同一分支。**
需要并行时，先拆分子任务、明确模块边界与接口，再由**唯一的集成责任位**整合结果。

## 8. 从双 Agent 扩展到多 Agent

本协议以**两个协作位**为基本模型。扩展时保持以下不变量：

| 不变量 | 内容 |
|--------|------|
| 状态单源 | 任务状态始终只有一个事实来源 |
| 实现者 ≠ 批准者 | 不因实例增加而放松 |
| 一任务一 Owner | 同一 Task 不被多实例同时写入 |
| 协作位可复用 | 新增实例仍归入两个协作位之一，不发明第三种位 |

扩展路径（不改变本协议的结构）：

```
2 实例：主控位 + 执行位
3 实例：主控位 + 执行位A + 执行位B（两者 File Scope 互斥）
N 实例：主控位 + 多个执行位（按模块/子系统划分边界）
```

---

## 9. 明确不做什么

- ❌ **不引入锁服务或分布式协调器** —— 冲突靠既有轻量机制，不靠外部组件。
- ❌ **不把协作位绑定到具体产品、模型或供应商** —— 协作位是职责集合，不是软件名称。
- ❌ **不允许同一实例在同一 Task 上自我批准** —— I2 不可被任何项目或任务规则削弱。
- ❌ **不重复定义角色** —— 角色职责与权限一律引用 `role-assignment.md` / `permissions.md`。
- ❌ **不假定平台会强制流程约定** —— 平台的真实强制力以 `github-capability-matrix.md` 为准。
- ❌ **不依赖聊天记忆维持任务状态** —— 一切协作依据必须落盘到文件。

---

## 与项目规则的关系

项目可在其 `AGENTS.md` 中声明：

- 本项目由哪些实例承担哪个协作位；
- 项目特有的边界与并行度限制。

**下列内容属于受保护约定，项目不得削弱：**

- I2（实现者 ≠ 批准者）；
- 高风险操作必须获得人类授权（`change-safety.md`）；
- 平台能力的如实披露要求（`github-capability-matrix.md` §4）。
