# Protocol: GitHub Capability Matrix

> 平台能力矩阵：**分清「文档要求的」「平台强制的」和「自动化实际能做的」**。
> **技术栈无关、项目无关。**
>
> **本文件只描述平台机制本身，不记录任何具体仓库的配置状态。**
> 每个项目的实际实测结果记录在**项目自己的能力记录文件**中
> （模板：`templates/github/GITHUB-CAPABILITY.md`）。
>
> 相关：`github-collaboration.md`（流程）、`../rules/github.md`（规则）、
> `change-safety.md`（高风险批准）、`dual-agent-model.md`（协作位）。

---

## 1. 必须在三个层面之间划清界限

| 层面 | 内容 | 强制力来源 |
|------|------|-----------|
| **① 文档制度** | 规则与协议文件中的「必须 / 禁止」 | **无强制力**，依赖遵守与审查 |
| **② 平台权限** | 账号实际可以执行哪些操作 | **平台强制** |
| **③ 自动化门禁** | 对代码、测试与合并条件的机器验证 | **机器强制** |

> ⚠️ **不得把文档中的禁止事项误认为平台已经强制限制了相应操作。**
> 「规则写了不许」与「平台不允许」是两件不同的事，必须在报告中分别陈述。

---

## 2. 平台机制能力矩阵

| 机制 | 能强制什么 | 生效条件 | 在本框架中的作用 |
|------|-----------|---------|----------------|
| **要求合并前必须经过 PR** | 阻断对默认分支的直接推送 | 需分支保护或规则集 | 使「禁止直推默认分支」从约定变为强制 |
| **要求状态检查通过** | 检查未通过时阻止改动进入默认分支 | 需至少一个检查已运行过并被选定；与「要求 PR」同时启用时最可靠 | 使 CI 成为**真门禁**而非提示 |
| **要求分支为最新** | 阻止「先绿后冲突」的合并 | 同上 | 防止通过陈旧结果绕过检查 |
| **要求批准（required approvals）** | 阻止未获批准的**合并** | **作者不能批准自己的 PR**；有管理员权限者**默认可绕过** | 仅在存在**第二身份**时才构成独立审查 |
| **不允许绕过上述设置** | 使规则对仓库所有者**也生效** | 需显式勾选 | 堵住默认绕过；同时带来自锁风险（§6） |
| **禁止强制推送** | 阻断 `push --force` | 分支保护 / 规则集 | 保护共享历史 |
| **禁止删除分支** | 阻断默认分支被删除 | 同上 | 防误删 |
| **CODEOWNERS** | **仅自动请求审查者** | 需仓库有写权限的对应身份 | ⚠️ **不创建独立身份、不启用审批、不阻止合并** |

> **关键区分：** 平台禁止的是**自我批准（approve）**，**不是自我合并（merge）**。
> 单一身份**可以**创建 PR 并自行合并（在未要求批准时）；
> 但它**不能**批准自己创建的 PR。
> 因此「单身份用不了 PR」是错误结论；正确的是「单身份得不到平台强制的独立审查」。

---

## 3. 强制力边界

### 3.1 平台**可以**强制

| 目标 | 实现手段 |
|------|---------|
| 默认分支不可被直接改动 | 要求合并前必须经过 PR |
| 检查必须先通过 | 要求状态检查 + 要求分支为最新 |
| 共享历史不可被改写 | 禁止强制推送 |
| 默认分支不可被删除 | 禁止删除分支 |
| 规则对所有者同样生效 | 不允许绕过上述设置（**注意 §6 的风险**） |

### 3.2 平台**不能**强制

| 目标 | 原因 | 补救 |
|------|------|------|
| **实现者 ≠ 批准者**（单身份场景） | 平台按**账号**判定，无法区分同一账号下的两个实例 | 换会话审查 + `Known Issues` 披露（`dual-agent-model.md` §5） |
| **变更是否经过实质审查** | 平台只能确认「有没有审批动作」，无法验证审查是否真实发生 | 审查证据必须落到 `handoffs/` |
| **提交信息、分支命名的规范性** | 平台不校验格式 | 由自动化检查承担（Level 2） |
| **高风险操作的人类批准** | 平台无此概念 | 制度门禁（`change-safety.md`） |
| **任务范围是否被遵守** | 平台不知道任务边界 | File Scope + 审查 |

> **结论：** 任何声称「平台会保证实现者与审查者分离」的表述都是错误的——
> 除非存在**第二身份**且已配置必需批准。

## 4. 制度-平台落差的披露要求

当某项文档约定**未被平台强制**时，必须**显式记录**，不得默认为已生效。

**披露位置（三处必须一致）：**

1. **项目能力记录文件**（模板：`templates/github/GITHUB-CAPABILITY.md`）；
2. **项目 `AGENTS.md`** 的 GitHub 章节；
3. **任务文件的 `Known Issues`**（当该 Task 依赖该约定时）。

**至少必须披露以下两类：**

| 类别 | 典型内容 |
|------|---------|
| 无平台强制的流程约定 | 「独立审查为流程约定，平台不强制」 |
| 依赖实测但未实测的机制 | 「必需检查是否能拦截直接推送：**未实测**」 |

> **禁止**把「计划中的配置」或「未执行的验证」描述为已完成。

---

## 5. 计划与可见性限制

**在启用任何平台保护前，必须先确认仓库的可见性与计划等级支持该机制。**

| 可见性 | 分支保护 / 规则集可用性 |
|--------|----------------------|
| 公开仓库 | 通常免费计划即可用 |
| 私有仓库 | 通常需要更高的计划等级 |

**规则集的例外名单（bypass list）** 在个人账号仓库中通常不可配，只有组织仓库可配。
→ 单账号 + 私有仓库的组合，可能**根本无法启用任何保护**。

**因此：** 启用保护前先验证可用性；不可用时**如实记录为「无法启用」**，不得声称已配置。

---

## 6. 自锁风险（必须知晓）

> **当「要求状态检查」与「不允许绕过」同时启用时，存在自锁风险：**
>
> 若某次提交**破坏了检查工作流自身**（例如工作流文件语法非法 → 检查永远不上报），
> 则「合并被阻断」与「直接推送被阻断」会**同时成立**，
> 常规手段**无法修复默认分支**，唯一逃生通道是所有者登录网页端修改或停用该规则。

**因此「不允许绕过」应被理解为：**

- ✅ **承诺机制** —— 让绕过成为一个需要刻意操作、可见且可追溯的动作；
- ❌ **不是「物理不可越」的保证**。

**缓解建议：** 变更检查工作流自身时，先确认新版本语法有效，再合并；并保留一次可执行的回退路径。

## 7. 需在平台侧人工完成的事项（通用清单）

以下事项**无法仅通过提交仓库文件完成**，必须在平台的网页界面、命令行或接口中单独配置。
**具体命令与操作步骤见 `shared/scripts/github_setup_checklist.md`。**

| 事项 | 载体 | 能否由提交文件完成 |
|------|------|------------------|
| 启用 / 关闭 Issue 功能 | 仓库设置 | ❌ |
| 分支保护 / 规则集 | 仓库设置 | ❌ |
| 必需状态检查的选定 | 分支保护 / 规则集 | ❌ |
| 不允许绕过 | 分支保护 / 规则集 | ❌ |
| 协作者与权限授予 | 仓库设置 | ❌ |
| 密钥与凭据 | 仓库设置 | ❌ |
| 工作流定义 | `.github/workflows/**` | ✅ |
| 交付请求模板 | `.github/**` | ✅ |
| 依赖更新配置 | `.github/**` | ✅ |
| 所有权声明（CODEOWNERS） | `.github/**` | ✅（但**不启用审批**） |

## 8. 待验证项登记表（模板）

各项目在启用保护后，必须**实测**下列项并把结论写回自己的能力记录。
**未实测前，一律标注「未实测」，不得默认成立。**

| 编号 | 待验证项 | 验证时机 | 若不成立的影响 |
|------|---------|---------|--------------|
| V1 | 状态检查能否拦截**直接推送**到默认分支（兴趣项） | 启用保护后 | 检查退化为提示 |
| V2 | 例外名单为空时，仓库所有者是否仍受约束 | 启用保护后 | 禁强制推送 / 禁删分支对所有者无强制力 |
| V3 | 检查是否在**合并之前**于工作分支上运行 | 首次交付时 | 检查无法构成门禁 |
| V4 | 必需检查未通过时，合并是否**确实被阻止**（阴性对照） | 首次交付时 | 门禁失效 |
| V5 | 必需检查**全绿**时，所有者（必需批准数 = 0）能否正常合并**自己的 PR**（阳性对照，与 V4 成对） | 首次交付时 | 门禁**误伤**合规交付（单账号仓库若误配批准数 ≥ 1，所有 PR 将永久无法合并） |

> **V5 的编号裁决（TASK-034，2026-10-15）：** V5 曾在多个文件被写成「直接推送默认分支是否确实被拒绝」。
> 该义被**弃用**：其信息已由 V1（检查角度）与 V2（所有者角度）双槽承载，且实测证据必然与 V2 行重复
> （同一次直推、同一份拒绝输出）；而「绿灯可合并」是 V4（红灯被阻）的**阳性配对**，
> 承载前四项均不覆盖的独立信息 —— 门禁**不误伤**合规交付。按「裁决须不丢信息」准则，保留后者。
> V1–V5 至此**一号一义、互不重复**。

## 9. 自动化可执行性边界

**必须调查当前环境真实支持的接口、事件、应用与命令，不得凭空设计不存在的自动化能力。**

| 能力 | 通常的前置 |
|------|-----------|
| 读取仓库与运行记录 | 只读凭据 |
| 创建分支 / 提交 / 交付请求 | **写权限凭据** |
| 修改分支保护 / 规则集 | **管理员权限** |
| 由平台事件**自动触发**本地 Agent | **需可达的 Agent 运行时**（通常不存在，需先建设） |
| 受控自动合并 | 分支保护 + 必需检查 + 发布与合并解耦 |

> **没有触发通道时，Level 3 不具备技术实现路径。** 此时应如实记录，而不是设计一个无法运行的自动化。

---

## 10. 明确不做什么

- ❌ **不把「合并」等同于「部署成功」或「业务验收完成」。**
- ❌ **不声称 CODEOWNERS 已启用审批机制。**
- ❌ **不声称创建了保护规则就获得了独立审查。**
- ❌ **不把未实测的机制写入制度并当作已生效。**
- ❌ **不虚构平台接口能力。**
- ❌ **不在「合并即发布」的场景下启用自动合并。**

---

## 与项目规则的关系

项目必须建立自己的**能力记录文件**（模板见 `templates/github/GITHUB-CAPABILITY.md`），内容包括：

1. 平台可见性与计划等级；
2. 已配置的保护机制及其实际状态；
3. §8 待验证项的**实测结论**；
4. §4 要求的落差披露。

**该记录属于「事实陈述」而非「规则」，不得被任何规则层的表述覆盖或美化。**
