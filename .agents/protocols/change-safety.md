# Protocol: Change Safety

> ⚠️ **受保护规则（Protected Rule）**
> 本协议定义高风险操作的强制流程。任何层级的规则**不得削弱**本协议。

---

## 1. 两类变更流程

### 普通变更（Normal Change）

低风险、可逆、影响局部。

```
Inspect → Plan → Modify → Verify
```

### 高风险变更（High-Risk Change）

```
Inspect → Explain → Backup → Approval → Modify → Verify
```

**关键差异：** 高风险变更在修改前**必须**有说明、备份与批准。

---

## 2. 高风险操作清单

| 类别 | 具体操作 |
|------|---------|
| **数据删除** | 删除数据库记录、删除表、清空数据 |
| **数据库迁移** | 结构变更、字段删除、类型变更、数据回填 |
| **生产环境** | 部署到生产、修改生产配置、重启生产服务 |
| **文件删除** | 删除文件、批量删除、清理目录 |
| **安全策略** | 修改认证/授权规则、修改密钥、修改防火墙 |
| **基础设施** | 修改网络、存储、计算资源、DNS |
| **大规模重构** | 跨模块结构变更、重命名公共 API |
| **Destructive Git** | `push --force`、`reset --hard`、`clean -fdx`、历史重写 |
| **权限变更** | 修改角色权限定义、修改访问控制 |

---

## 3. 高风险流程详解

### Step 1 — Inspect（检查）

- 明确要改什么、为什么改。
- 确认影响范围（哪些文件、哪些服务、哪些数据）。
- 确认是否有替代的低风险方案。

### Step 2 — Explain（说明）

必须向人类（或授权的审批者）说明：

| 项 | 内容 |
|----|------|
| 目标 | 为什么要做这个变更 |
| 范围 | 影响哪些资源 |
| 风险 | 可能出什么问题 |
| 不可逆性 | 是否可回滚 |
| 回滚方案 | 如何回滚 |
| 验证方式 | 如何确认成功 |

### Step 3 — Backup（备份）

- **在修改前**创建备份。
- 确认备份**可用**（不只是创建了，还要验证可恢复）。
- 记录备份位置。
- 无备份 → **不得进行不可逆的高风险变更**。

### Step 4 — Approval（批准）

- 高风险变更必须获得**人类显式批准**。
- 批准必须是针对**本次具体变更**的，不能是笼统的"以后都可以"。
- 未获批 → 不得执行。

### Step 5 — Modify（修改）

- 按批准的范围执行，**不扩大范围**。
- 小步执行，便于定位问题。
- 记录每一步。

### Step 6 — Verify（验证）

- 确认变更达到预期效果。
- 确认未引入副作用。
- 确认备份仍可恢复。
- 记录结果。

## 4. 删除文件的特别约束

删除文件是常见但危险的操作。

**强制规则：**

1. **禁止**递归删除用户个人目录（Desktop / Downloads / Documents / Home）。
2. **禁止** `rm -rf` 作用于宽泛路径（如 `/`、`~`、`C:\`）。
3. 优先使用**可恢复方式**：
   - 版本控制（`git rm`，可恢复）
   - 系统回收站（macOS `trash`、Windows 回收站、Linux `gio trash`）
4. 批量删除 → 先**列出清单**，再分批执行（每批不超过 10 个），每批后验证。
5. 删除前**必须**确认目标路径精确无误。

**个人目录扫描规则：**

> 若被要求扫描/清理个人目录 → 默认**只读**，只产出报告，不执行任何修改。
> 必须由人类明确指定要处理的文件后才可行动。

---

## 5. 数据库迁移的特别约束

1. 迁移脚本必须**幂等**或可安全重跑。
2. 必须提供**回滚迁移**。
3. 在生产执行前，必须先在**结构相同的测试环境**验证。
4. 大表变更必须评估锁与性能影响。
5. 数据回填必须可中断、可续跑。
6. 备份必须在迁移前完成并验证。

---

## 6. 生产环境变更的特别约束

1. **默认禁止** Agent 直接操作生产。
2. 必须人类批准。
3. 必须有回滚方案并已演练。
4. 必须在低峰期执行（如适用）。
5. 必须有人（或 Agent）在变更期间**值守观测**。
6. 必须记录发布记录。

---

## 7. Destructive Git 的特别约束

| 操作 | 约束 |
|------|------|
| `push --force` | 共享分支禁止；个人分支需说明并确认 |
| `reset --hard` | 先确认无未提交改动，或已 stash |
| `clean -fdx` | 先 `-n` 预演，确认将删除的文件清单 |
| 历史重写 | 仅限未推送的本地历史；已推送需人类批准 |

---

## 8. 判定流程

```
准备执行某操作
      │
      ▼
是否在高风险清单中？
      ├─ 否 → 走普通流程：Inspect → Plan → Modify → Verify
      └─ 是 → 走高风险流程：
                Inspect → Explain → Backup → Approval → Modify → Verify
                      │
                      ▼
              是否已获人类批准？
                ├─ 是 → 执行
                └─ 否 → 停止，等待批准
```

---

## 9. 不确定时怎么办

> **若不确定某操作是否属于高风险 —— 按高风险处理。**

宁可多走一次审批，也不要造成不可逆的损失。

---

## 10. 事故处理

若高风险操作导致问题：

1. **立即停止**后续操作。
2. 评估影响范围。
3. 执行回滚（若可行）。
4. **如实记录**事故（不隐瞒）。
5. 复盘根因，更新本协议或相关规则。

---

## 覆盖规则

- ✅ 项目可以**增强**（如"本项目所有数据库变更都需批准"）。
- ❌ 项目**不得削弱**本协议任何约束。
- ⚠️ 修改本协议需**人类批准**。
