# Protocol: Rule Precedence

> 定义规则的继承与冲突裁决机制。**这是框架最核心的协议之一。**

---

## 1. 问题

规则分布在多个层级：

```
Workspace → Project → Task → Directory → 当前任务上下文
```

当不同层级给出**冲突**的要求时，必须有一个确定的裁决规则。
朴素的线性继承（"最具体的总是获胜"）存在缺陷：
**它允许低级规则削弱安全约束。**

---

## 2. 双轴模型

规则沿两个轴评估：

### 轴 A — 约束轴（Constraint Axis）

部分规则是**受保护规则（Protected Rules）**，代表安全与系统级约束：

| 受保护规则 | 文件 |
|-----------|------|
| Security | `.agents/rules/security.md` |
| Git 禁止操作 | `.agents/rules/git.md` §6 |
| 测试禁止事项 | `.agents/rules/testing.md` §6 |
| 职责分离 | `.agents/protocols/permissions.md` §3 P3 |
| Change Safety | `.agents/protocols/change-safety.md` |

> **为什么「职责分离」在表内：** 它约束的不是"能不能做"，而是"**谁来做**"。
> 一旦允许实现者批准自己的实现，审查就退化为自我确认 ——
> 这属于**降低对风险的防护**，符合 §5 的削弱判定。
> 具体分配方案（角色家族 / Agent 数量不足时怎么办）见 `role-assignment.md`。

**受保护规则的行为：**

- 永远生效，不受层级影响。
- **只能被增强，不能被削弱。**
- 冲突时一律采用**更严格**的一方。

### 轴 B — 特化轴（Specificity Axis）

非受保护规则按**具体性**覆盖：

```
② Workspace 规则  （最一般，提供默认值）
      ↓ 可被覆盖
③ Project 规则
      ↓ 可被覆盖
④ Task 规则
      ↓ 可被覆盖
⑤ 目录级规则
      ↓ 可被覆盖
⑥ 当前任务上下文 （最具体，优先级最高）
```

---

## 3. 最终优先级

```
① 受保护规则（Protected）           ← 绝对优先，不可削弱
        │
        ▼
② Workspace 规则                    ← 通用默认值
③ Project 规则                      ← 覆盖 ②
④ Task 规则                         ← 覆盖 ③
⑤ 目录级规则                        ← 覆盖 ④
⑥ 当前任务上下文                    ← 覆盖 ⑤
```

**读法：** 先检查是否有受保护规则适用（①）。若无，则在 ②–⑥ 中取**最具体**的一层。

---

## 4. 冲突裁决算法

```
给定冲突 C：
  1. C 是否涉及 security / safety / system 约束？
       是 → 采用更严格的一方。结束。
  2. C 是否涉及受保护规则（git §6 / testing §6 / permissions §3 P3 / change-safety）？
       是 → 采用受保护规则。结束。
  3. 否则：
       采用层级更具体的一方（② < ③ < ④ < ⑤ < ⑥）。
  4. 仍无法判定？
       → 停止。记录冲突（含双方原文与出处），请求人类裁决。
       → 不得自行猜测。
```

---

## 5. 增强 vs 削弱

判断某变更是否"削弱"受保护规则：

| 变更 | 判定 |
|------|------|
| 项目要求"所有变更需双人 Review" | ✅ 增强 |
| 项目要求"本项目禁用某类危险 API" | ✅ 增强 |
| 项目要求"本项目的密钥可硬编码以便测试" | ❌ 削弱 |
| Task 要求"跳过测试以加快交付" | ❌ 削弱 |
| 目录规则要求"此目录允许 force push" | ❌ 削弱 |

**判定原则：** 若变更**减少**了对某项风险的保护 → 削弱 → 拒绝。

---

## 6. 声明覆盖的方式

项目 / Task 覆盖规则时，必须**显式声明**，不得隐式覆盖：

在项目 `AGENTS.md` 中：

```markdown
## Project-specific Rules

- [覆盖] Workspace `coding.md` §4：本项目允许在测试中使用魔法值。
- [补充] 所有 API 必须返回 RFC 7807 格式错误。
- [增强] 所有变更需通过安全扫描。
```

在 Task `TASK.md` 中：

```markdown
## Task Rules
- [覆盖] 本任务临时放宽 lint 规则 X（原因：...）。
```

**未显式声明的覆盖一律无效。**

---

## 7. 规则定义者的义务

- **单一事实来源**：一条规则只在一处定义。
- 其他位置**引用**而非复制。
- 修改规则时必须检查是否有引用方需要同步。
- 不得在 Workspace 层写具体技术栈规则（见 `AGENTS.md` §2 P4）。

---

## 8. 示例

**场景：** Workspace 要求"提交信息使用 Conventional Commits"；
某项目要求"提交信息使用中文描述"。

- 该规则非受保护 → 走特化轴。
- Project 比 Workspace 具体 → 采用 Project 的要求。
- 结论：该项目提交信息用中文描述（但仍应保持 Conventional Commits 的结构前缀，因为结构前缀未被覆盖）。

**场景：** 某 Task 要求"为赶进度，先不写测试"。

- 涉及 `testing.md` §6（受保护）→ 采用受保护规则。
- 结论：**拒绝**。测试不可省略；若确实无法测试，须在 Handoff 中显式说明并获批准。
